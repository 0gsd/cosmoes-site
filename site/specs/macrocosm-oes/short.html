MacroCOSM OES

Edition 0.6.0 · revised 2026-11-06 · cosmoes.org home: https://macro.cosmoes.org/

This edition describes grammar version 0.6.0; files written under 0.5.4, 0.0.2 and 0.0.1 are read unchanged.

MacroCOSM OES is an OES: a shared grammar and the core built into it. The grammar says how a domain is enumerated as plain-text .cosm files that are at once a file system and a relational database, made to be rendered: how a file is read, how a volume names the format it is written in, what an item is and which columns every item carries, how one item points at another, how an unknown value is written down, how anything is addressed, which checks every volume can be held to, how a manifest declares a format, and how a renderer draws one. It is the grammar that Comprise OES worked out for companies, read out of it and written down on its own, so that nothing in it says "company". The core holds five built-ins, written in the grammar and declared by manifests that ship with every reader: the product tree (cosm), Canon, the home file system (canon), the fabula (fabula), documents (doc) and Thym's volumes (thym), with the densities and the dialectic (section 18). Two MiniCOSMs, Comprise OES for companies and Ascribe for a person, are written in it with specifications of their own (section 19).

Status. This text is normative. Its reference implementation is enough (https://github.com/0gsd/enough), which reads every format registered in sections 18 and 19; Comprise is the reference implementation of Comprise OES. Where an implementation and this text disagree, one of them is in error; the Changes appendix (section 21) records which was corrected. By reference marks a part that is defined in another document, which is linked where it is named.

The format does not change. A MacroCOSM file is a .cosm file in the COSM YAML subset, exactly as Comprise OES reads it. Version 0.0.1 names the grammar, generalizes it, and adds a few optional manifest keys so that a reader can handle a format it has never seen without new code (section 13.5). Every Comprise Holotype and every standalone COSM tree written under an earlier version reads unchanged.

How to read this

Must and may. Must is a rule a conforming reader or writer keeps. May is a permission. Should is advice the checks do not enforce.

Words. The words a person reads on screen come first. Where the spec must be exact, the term the files and the reader use follows in parentheses.

Here In the files and the reader Example
item node, a mapping in a nodes: list P:claim/close-locks-the-day
kind type, the type: field claim
open question pending {pending: "…"}
checks lint enough's lint command, run over a volume
volume the database a catalog heads a Holotype, a Canon volume, a text's fabula
part a top-level division of a volume (Comprise: concern, atom) atoms/meadow/

Examples. Every block in this document marked cosm is one complete file: it starts with its declaration, it loads, and it passes the checks its format selects, with every reference resolving inside the block. A block marked yaml is a fragment of a file and may point at things outside it. A block marked text is grammar or a picture.

The earlier specifications stay where they are. COSM 0.2 is the context-ontology skill's own reference. This document points at their section numbers and does not repeat them.

1.2 The name

COSM is the family's name. It is no longer an acronym. It was Context Ontology Schema and Markup, and before that OPI; both are history. It comes from kosmos, the Greek word for order, and for the world as an ordered whole. .cosm is the family's one file extension.

OES stands for organizational enumeration system: a system that organizes a domain by enumerating everything in it, as a file system that is also a relational database, made to be rendered. Each of the four parts of that sentence is a promise.

  • Enumerating. It lists what there is, item by item, each with its sources. What is not known is written as an open question addressed to whoever can answer it, never as a guess.
  • A file system. Plain text files in folders, on the owner's own machine. Anyone can read them without an app, move them, keep them in version control, and leave with everything.
  • A relational database. Every item has a primary key, its id. Its fields are columns, its references are foreign keys, and the checks are constraints. The same files can be indexed and queried.
  • Made to be rendered. The description is never the end. It exists to be turned into other forms for other readers: a drawing, a summary, a text rewritten for one audience, an export for an agent, a public projection. A renderer can show only what the description holds, so the description is held to account.

MacroCOSM, MiniCOSM and MicroCOSM are the three scales of the family (section 3). The names borrow an old idea, from Greek philosophy to the Renaissance: that a small world mirrors the order of the great one. Here each smaller scale keeps the order of the larger and adds to it.

1.3 Stewardship

MacroCOSM OES is stewarded by Verroes (Graham Smith). The specification, the manifests registered in sections 18 and 19 and the names of the family are his (see the colophon). Its canonical edition is published at https://macro.cosmoes.org/; each edition says what changed in the Changes appendix (section 21). What is real in each reading. The file system is the volume itself: plain text, canonical. A format may keep a local database beside its files for what must never be in a file (Comprise keeps its people there); that database is outside the model (section 6.6).

The one rule that makes both readings agree: a path names the same thing a primary key does (section 11).

3. Scales: MacroCOSM, MiniCOSM, MicroCOSM

Scale What it is In this edition
MacroCOSM an OES: the shared grammar, and the core built into it this document, and its reference implementation, enough
MiniCOSM a domain's OES with a specification of its own, declared by a manifest: its volume layout, modules, kinds, fields, references, checks and renderers two: Comprise OES (comprise, companies) and Ascribe (ascribe, a person) (section 19)
MicroCOSM one organization's extension on top of a MiniCOSM: the extra kinds, fields, checks or renderers it needs reserved for a later edition (section 17)

The core is what MacroCOSM holds built in: the grammar's parts, five built-ins, the three densities and the dialectic (section 18).

A built-in is a kind of volume the core defines, declared by a manifest that ships with every reader and says core: true (section 13.3): cosm/0 the product tree, canon/1 Canon, the home file system, fabula/1 the fabula, doc/1 documents and thym/1 Thym's volumes. A built-in is never a MiniCOSM, and a MiniCOSM is never built in.

A format is what a declaration names: a built-in or a MiniCOSM (section 5). Wherever this document states a rule for a format, the rule holds for both.

What MacroCOSM gives every format. All of it, unchanged: sections 4 to 14 of this document, the parts defined by reference in sections 15 to 17, and the core's dialectic, whose module every format inherits (section 18.6).

What a format declares. Its manifest (section 13) says, in order: its name and version and the declaration a volume uses to name it, with any legacy forms and old spellings it still reads; whether it is built in; its volume layout; its modules and kinds, and for each kind at least the fields the checks follow; its reference forms and closed lists; the checks that apply, with their severities; its renderers and lenses; the opening questions of its dialectic, when it has any; and, when it has one, its public projection. A volume names its format with one line in its catalog and never embeds the manifest.

Each smaller scale keeps the order of the larger. A format may add to the grammar (kinds, fields, envelope fields, closed lists, checks, renderers) and may narrow what the grammar leaves open (which envelope fields are required, which link relations are allowed). It may not change what the grammar means: an id, a path, a reference, an open question and the declaration mean the same thing in every format.

4. The file format

4.1 Encoding and shape

  • A .cosm file is UTF-8, with or without a byte-order mark. CRLF and LF read the same.
  • A file is one YAML document whose top level is a mapping. An empty file reads as an empty mapping.
  • A file that does not parse, or whose top level is not a mapping, is a load problem (check load, section 12). The rest of the volume still loads. A reader never stops at the first problem; it collects every load problem and the checks report them as errors.

4.2 The COSM YAML subset

The subset is YAML without the parts that make a file mean something other than what it says.

Forbidden Why A reader
anchors (&name) and aliases (*name) one value in two places hides a reference that the checks cannot see reports a load problem
tags (!!str, !thing) a tag changes how a value is read; the subset has one way reports a load problem
more than one document in a stream (--- between documents) a file is one mapping reports a load problem

A reader must not crash on a forbidden construct, and must name it in the problem. A writer must not produce one (section 4.5).

4.3 Scalars

  • Booleans are YAML 1.2's: true and false, in lower, title or upper case (true, True, TRUE). The YAML 1.1 words yes, no, on and off are strings. (A field called on: depends on it.)
  • Everything else resolves exactly as PyYAML's SafeLoader resolves it: integers, floats, nulls and timestamps included. Those rules are YAML 1.1's, so a few plain scalars are not what they look like.
Written Read as So
2019-03-01 a date a date field is a date, not a string
2026-10-22T09:15:30Z a date and time, in UTC
cosm: 0.3 the float 0.3 a version compares as text (0.3), never as a number
macrocosm: 0.0.2 the string 0.0.2 (a reader keeps 0.0.1 as it is)
0.10 the float 0.1
7:00 the integer 420 (base 60) write times quoted: "07:00"
012 the integer 10 (octal) write codes with leading zeros quoted: "012"
~, null, nothing after the colon null
yes, on the strings yes, on

The reference loader is a few lines of Python. It is SafeLoader with the YAML 1.1 boolean resolver removed and a YAML 1.2 one put back, exactly as Comprise reads its Holotypes:

import re, yaml

class Loader(yaml.SafeLoader):
    """SafeLoader with YAML 1.2 booleans: only true and false, in any of three cases."""

Loader.yaml_implicit_resolvers = {
    first: [(tag, rx) for tag, rx in resolvers if tag != 'tag:yaml.org,2002:bool']
    for first, resolvers in yaml.SafeLoader.yaml_implicit_resolvers.items()}
Loader.add_implicit_resolver('tag:yaml.org,2002:bool',
                             re.compile(r'^(?:true|True|TRUE|false|False|FALSE)$'), list('tTfF'))

A second implementation in another language must reproduce these results, not YAML 1.2's own core schema.

4.4 Comments and style

  • Comments are YAML's #. A reader ignores them; a semantic rewrite loses them (section 4.5).
  • Block scalars (|, >) are legal for long prose.
  • Flow mappings and sequences are idiomatic for short records: provenance: {mode: derived, sources: [x], confidence: 0.8}. A comma inside a flow value ends the value, so a value with a comma is quoted.
  • Key order carries meaning in one place only: the declaration is the first key of a catalog (section 5). Elsewhere a reader ignores order and a writer keeps it.
  • A # inside a plain scalar is a comment only when a space comes before it. Locators such as close.md#L3 are safe unquoted, and are quoted in this document for clarity.

4.5 Writing

  • A writer dumps with yaml.safe_dump(data, sort_keys=False, allow_unicode=True, width=110), or an equivalent that produces the same subset.
  • The declaration is written first.
  • A dumper emits an anchor when the same object appears twice in the data. A writer copies values instead of sharing them, so no anchor is ever written.
  • A writer quotes every scalar meant as text that the loader would read as something else (section 4.3).
  • A semantic rewrite (load, change, dump) keeps every key and value and loses comments and layout. Byte-preserving edits of one item inside a file are Comprise's (its edit model); MacroCOSM reserves them for a later edition.

4.6 Text, not code

A .cosm file is data. A reader never executes anything in it, never follows an include, and never opens a file because a value names it, except where the manifest's volume layout says where the files of a volume are (section 6). A path is an address, never a door (section 11.2).

5. The declaration

5.1 The form

A catalog says which format it is written in with its first key:

oes: canon/1

declaration = "oes:" SP format "/" major
format      = lower *( lower / DIGIT / "-" )          ; the format's name, as its manifest gives it
major       = "0" / ( %x31-39 *DIGIT )                ; the format's major version, an integer

The value names a format, a built-in or a MiniCOSM (section 3), and a major version, never a minor one. It is spelled exactly as the manifest's declaration.value gives it, or as one of the old spellings the manifest lists (section 5.2), and a reader refuses any other spelling, as Comprise does: comprise/01 is refused, and so is a value with a space before or after it. A change to a format that existing volumes can still be read under keeps its major; a change that would make an existing volume mean something else needs a new major, and a change that would alter what a path means needs a new format (section 11.3).

5.2 Identifying a catalog

The reader keeps a registry of the manifests it knows (section 13.6), in order: comprise, cosm, canon, fabula, doc, then any other in name order (ascribe, thym). Given a catalog, it decides which format the catalog is written in by these steps, in order. The first that applies decides, and the reader reports which step it was: oes, old, legacy or absent.

  1. An oes: key decides. If its value is a string naming a format in the registry and a major that manifest declares, the catalog is written in it. If its value is one of the old spellings a manifest's declaration.old lists, the catalog is written in that manifest's format, and the reader reports it as identified old. Anything else under oes: (an unknown name, an unknown major such as comprise/2, a value not spelled exactly, such as comprise/01 or ' emf/1 ', an empty value, a value that is not a string) is refused.
  2. A legacy key. If the catalog has no oes: key, each manifest's declaration.legacy keys are tried in registry order. The first manifest that names a key present in the catalog (and, where it gives one, a matching value) claims it. Values compare as text, so comprise: 0.1 matches the legacy value '0.1'.
  3. An absent default. A manifest whose declaration.absent names its own declaration (Comprise's says comprise/1) claims a catalog with neither key, but only a catalog found where that manifest's volume.catalog puts it: holotype.cosm at the root of a folder, for Comprise. A default never claims a file at another name.
  4. Otherwise the catalog is refused: it declares nothing the reader knows.

When a catalog carries both oes: and a legacy key, oes: decides and the legacy key is kept and ignored (Comprise's declaration.both: oes).

Old spellings. An old spelling is an oes: value under an earlier name of a format, which its manifest reads and never writes: the manifest lists it in declaration.old (section 13.3). A format keeps its paths, so a volume under an old spelling means exactly what it would mean under the format's own value. The fabula is the worked case. Its manifest declares fabula/1 and lists emf/1 as old, so a twin written as

oes: emf/1
id: emf/guides--close-md

is a fabula. The reader reports it as identified old; its items, paths and checks are the fabula's; its catalog id keeps the old prefix and gives the same database name, guides--close-md (section 6.2); and a URI may name it either way (section 11.3). The file keeps saying oes: emf/1 (section 5.5).

5.3 Refusal

A refused catalog loads nothing. The reader returns a refusal, a value that says what the catalog declares and what the reader knows, and never raises. For example:

canon.cosm declares oes: canon/2, which this reader cannot read: this reader reads Canon as canon/1 only; nothing was
loaded

The checks report the refusal as one load error, and a viewer shows it in place of the volume.

5.4 Legacy forms

The core's built-ins:

Format Declaration Old spellings Also read Absent
cosm oes: cosm/0 none cosm: 0.2, cosm: 0.3, and opi: with any value refused
canon oes: canon/1 none nothing refused
fabula oes: fabula/1 oes: emf/1, read as a fabula whose flavour is fabulan (section 18.4) nothing refused
doc oes: doc/1 none nothing refused
thym oes: thym/1 none nothing refused

The MiniCOSMs:

Format Declaration Old spellings Also read Absent
comprise oes: comprise/1 none comprise: 0.1, the line in every Holotype made before Comprise OES 1 holotype.cosm with no key reads as comprise/1, silently
ascribe oes: ascribe/1 none nothing refused

A legacy key and an old spelling are never errors. A reader keeps them.

5.5 Writing the declaration

  • A writer creating a volume writes the declaration as the first key of its catalog, so a person or a tool sees it without parsing the file.
  • A writer writes a format's own value, never an old spelling: a new fabula says oes: fabula/1, never oes: emf/1.
  • A writer must not rewrite the declaration of a volume it did not create. There is no migration: a Holotype that says comprise: 0.1 keeps saying it, and a twin that says oes: emf/1 keeps saying it until its text is decompiled again and a new twin is written in its place (section 18.4).

5.6 The reserved key macrocosm:

A catalog or a manifest may carry macrocosm: 0.6.0 (or an earlier 0.5.4, 0.0.2 or 0.0.1), after its declaration. Readers keep the key and ignore it. It is reserved for the day the grammar itself needs a version test; until then no reader refuses a file for what it says, and no writer is required to write it.

6. Volumes and catalogs

6.1 Volumes

A volume is one database of a format. It has one of two shapes, and the manifest's volume block says which.

Shape What it is Its items Formats
a folder volume a folder with the catalog at its root and module files below it, in the places the manifest's volume block names in module files, under nodes: (and, where a format says so, a named block such as brand:) built in: cosm (a product tree); MiniCOSMs: comprise (a Holotype), ascribe (a holograph)
a single-file volume (volume.single-file: true) one file: the catalog is the whole volume under the catalog's own nodes: built in: canon (a Canon volume's canon.cosm), fabula (a text's twin, or the fabula beside a folder of code), doc (one telling of a document), thym (a program's volume, a morph, a context, a plan, a trace or a package)

A fabula of code describes a folder, but the fabula itself is one file beside it: the folder is its source, not its volume.

A volume is what a URI names (section 11.3), what the checks run over, and what a renderer draws. Two volumes never share an item: a reference between volumes is written as a URI, and the reader does not resolve it (section 9.3).

6.2 The catalog

The catalog is the file at the root of a volume that declares the format and says what the volume holds. It is one YAML mapping.

  • The declaration comes first (section 5).
  • The keys a catalog may hold are the manifest's catalog.keys. A reader keeps every key, listed or not, and ignores the ones it does not understand. A key the manifest does not list is reported by the check catalog-key as a note. A writer must not invent catalog keys the manifest does not list without a new version of its format.
  • The catalog id has the form the manifest's catalog.id gives: holotype/<slug>, canon/<volume-slug>, fabula/<slug>. A manifest may also list earlier forms in catalog.id-old, read and never written: the fabula's is emf/<slug>, so an old twin's emf/guides--close-md is read as it is. When the id is absent, the manifest's catalog.id-absent rule supplies it (Comprise: holotype/<folder name>). The id without its prefix, the current one or an old one, is the volume's database name, the second segment of its URI. A catalog with no id fails catalog-key where the manifest's catalog.id is a template, and where the manifest gives catalog.id-absent the reader supplies the id. Where a manifest gives both, the template wins: catalog-key reports the missing id as an error, and the reader still supplies the id, so the volume keeps a database name.
  • Sources. A catalog may declare the sources its items cite (Comprise's sources:, with the fields the manifest's catalog.source-fields lists). Where a format checks that cited sources are declared, the check is its own.

6.3 The volume block

The manifest's volume block says where the files of a volume are (its keys are listed in section 13.3): the catalog's file name, whether the volume is a single file, where a folder volume's parts, modules and module files are, and what is outside-the-model. Files and folders outside the model sit inside the volume but are not part of it: they are not read as module files, not checked, and skipped by a tool that copies the model elsewhere (Comprise's people.yaml, feeds/ and scans/; Canon's .canon.json). Keys a format adds for its own code (Comprise's vendors, snapshots, database) are kept.

6.4 Parts

A format may divide a folder volume into top-level parts, each with its own modules. Comprise does: each concern (atom) is a part, at atoms/<concern>/, declared in the catalog's atoms: list. A declared part without its folder is a load problem; a folder under the parts' place that the catalog does not declare is a load problem.

An item belongs to exactly one part. Inside its own part an id is written bare; from another part it is written qualified, <part-prefix>//<id> (section 11.1). A volume without parts (every single-file volume, and the standalone product tree) has one implicit part, and its paths have no part segment (section 11.2).

6.5 Module files

In a folder volume, a module file is a .cosm file in the places the manifest names, at any depth. Each is one mapping with one of the shapes the manifest's module-file.shapes lists. The two every format may use:

nodes:                          # the items, each a mapping with a string id
  - id: O:role/Founder
    type: role
    name: Founder

module: none                    # this module is empty on purpose
reason: people are never written into a file
  • File names are free. No id and no path names a file; the file an item is written in is metadata. Moving an item to another file changes neither its id nor its path.
  • Order. Files are read in path order, compared case-insensitively; items keep their order within a file.
  • Duplicates. An id already loaded in the same module of the same part is a load problem; the first wins (check duplicate-id).
  • module: none carries a reason. Without one it is a warning (check module-none), and the reason reads "no reason given".
  • An empty module (no folder, or a folder with no items) is legal.

In a single-file volume there are no module files. Every item is in the catalog's nodes: list, and its module is the letter at the start of its id.

6.6 What is never in a file

A format may keep some of what it describes out of its files on purpose. Comprise keeps people only in a sealed local database beside the Holotype, and marks the kinds that live there stored: database in its manifest. A reader never reads such kinds from a file, and a writer never writes them into one. The local database, where there is one, is outside the model: the checks do not read it unless a format's own checks say so, and no export of the files includes it.

7. Items, kinds, fields

7.1 Items

An item is a row: a mapping with a string id and a type. It is written in a nodes: list, or in a named block a format declares (Comprise and the product tree hold the brand under brand:, and read a legacy firm: the same way). An entry of a nodes: list that is not a mapping, or has no string id, is a load problem; the rest of the file still loads.

An item's id never changes. Its name is for display and may change freely.

7.2 Modules

A module is a group of kinds: a group of tables. It is named by one capital ASCII letter, and the manifest gives it a name and a short subtitle: the fabula's P is Propositions, "what the text claims, and how it knows".

Letters are local to a format. The declaration says which format a volume is written in, and so which module a letter names. P is Products in comprise and in the product tree, and Propositions in the fabula. The grammar reserves one letter only: D is the dialectic's in every format, and a format whose manifest does not declare it inherits the core's (section 18.6).

Format Modules
cosm (built in) P Products
canon (built in) V Volume
fabula (built in) I Inspiration · L Lexicon · E Entities · K Concepts · N Intent · C Construction · R Production · P Propositions · T Transitions · X Atems
doc (built in) S Structure · T Terms · R Reference · B Bubbles
thym (built in) P Programs · M Morphs · C Contexts · R Runs · K Packages
comprise (MiniCOSM) C Corporation · O Organizations · M Markets · P Products · R Representations · I Inventories · S Stacks · E Employees
ascribe (MiniCOSM) A Affinities · B Beliefs · C Concerns · E Experiences · I Interests · O Opinions · Q Qualia · S Skills · U Understandings · Y Yearnings · F Forms

7.3 Kinds

A kind is a table. It is declared under its module, with:

Key Holds
refs the kind's reference fields: the fields the reference checks follow (section 9). An empty list says the kind has none
checked further fields a check reads, beyond the envelope
required the fields an item of the kind must carry (section 13.5)
flavours in a format with flavours (the fabula's, section 18.4), the flavours whose volumes may hold the kind; the check flavour-kind reads it
closed closed lists for the kind's own fields, {<field>: [values]}, applied to items of the kind over the manifest's closed-lists (section 13.3)
other keys what a format's own code needs: a level, an exception id form (id: 'P:<slug>'), stored: database, public: never, a note

An item's type must be a kind its module declares (check type), and must equal the kind in its id (check type-prefix), except where the manifest declares an exception form (Comprise's brand, P:<slug>, whose id has no kind). A manifest may map legacy kind names to current ones (Comprise reads firm as brand and stack as function); a reader applies the map before checking and reports the legacy name as a note.

7.4 Fields

A field is a column. Every key of an item is a field.

  • Field paths. A field inside a field is addressed by its field path: keys joined by ., list positions written [n], counted from zero. flow.outputs[0].to is the to of the first output. The same field path addresses an open question (section 10) and follows # in a path (section 11.2).
  • Dotted reference fields walk into lists and mappings. A kind that lists rows.sku as a reference field means the sku of every row.
  • Wildcard fields. A reference field ending in .* names every value of a mapping (0.0.1). The fabula lists roles.*: every value under a claim's roles: is followed (section 9.6).
  • Unknown fields are kept, always. A field the manifest does not declare is legal. A reader keeps it, shows it, and never drops it; a writer that rewrites an item keeps it.
  • Absent and none. A format should read an absent field as "not yet asked", never as "nothing". Where nothing is the fact, the item says none.

8. The envelope

8.1 The columns every item has

The envelope is the set of columns every item carries, whatever its kind: the system columns of every table. MacroCOSM's minimum envelope is nine fields.

Field Holds Default check
id the item's id (section 11.1) id-grammar, id-module, duplicate-id
type its kind type, type-prefix
name a label for display identity-min when required
summary one sentence saying what it is identity-min when required
status where it stands in its life status
visibility who may see it visibility
provenance how it is known, from what, how surely provenance
pending an open question about the whole item (section 10) pending-shape

A format declares which envelope fields every item must carry, in its manifest's envelope.required. A required field that is missing fails the check identity-min; only presence is checked, as in Comprise, so an empty value passes.

8.3 Envelope fields a format adds

A format may add fields to its envelope (envelope.fields) and say which of them are references (envelope.references). Comprise adds owner (a role, never a person), since, until, mattering, body, at, attributed-to, template, instances, counterparty, series and shared-with, and checks owner, at, attributed-to, counterparty, shared-with and links as references. Canon adds path, parent, parts, size, mtime, kind, twin, fabula and atem. The fabula adds span, salience and withheld. DocOES adds atem, body, lines, order and chapter, and checks chapter as a reference. Thym adds made. Ascribe adds span, form, of, parts, when, valence, strength and made.

MacroCOSM's envelope has no owner. An owner is Comprise's addition, a role that answers for an item, and a format without roles (a fabula, a file, a holograph, whose holder is its subject) has nothing to put there.

8.4 Status and visibility

Unless a manifest gives other lists, the closed lists are Comprise's:

Field Values
status active · dormant · planned · retired
visibility public · internal · restricted

What an absent visibility means is the format's to say (Comprise: internal outside P, by level in P). Whatever it says, these rules hold for every renderer:

  • A hidden item is absent, not refused: lists leave it out, a renderer never draws it, and a reference to it from a visible item keeps the id and gains no name.
  • An id is an address, not a secret.
  • A path to a hidden item answers exactly as its id would (section 11.2).

8.5 Provenance

Sources or it didn't happen. provenance is a mapping:

Field Holds Checked
mode how it came to be known, from the closed list below error otherwise
sources a non-empty list of what it came from: source ids the catalog declares (Comprise), or locators in the source text (a fabula: 'close.md#L3-L7') error when empty or not a list
confidence a number from 0 to 1 error otherwise
state known (the default) · pending · not-disclosed · stale error otherwise
other fields what a format adds (Comprise: synced-from, synced-at, max-age) as that format says

Modes, Comprise's twelve: dialectic · net-scan · system-scan · integration · structured-intake · manual · derived · asserted · archetype · catalogue · directory · accounting. derived is the mode every derivation uses: an item a program made from other material, such as a fabula's item made from a text. dialectic is the mode of what a person's answer wrote, through the core's dialectic (section 18.6).

An item may also carry provenance.answered, {<field path>: {sources, confidence}}: the fields an answer of the dialectic filled in an item made some other way, each with its session and the person's confidence; and withheld, a list of the field paths its subject declined to give (section 18.6.4).

not-disclosed is a fact, not a question: the subject declined to say. pending says the item stands on something not yet confirmed.

Identity instead of provenance. The product tree carries COSM's identity instead of a provenance block: confidence and sources at the top level of the item, with owner required. The manifest says so (Comprise's envelope.identity-in-P), and the provenance check then reads those two fields where they are.

8.6 Unknown fields

Allowed, and kept. The envelope is a floor, not a ceiling.

9. References and links

9.1 What a reference is

A reference is an id written in a reference field: a foreign key. The reference fields are the kind's refs (section 7.3) and the envelope's references (section 8.3). A value in a reference field takes one of these forms:

Form Example Names
bare O:role/Founder an item in the same part
qualified atom/mozilla-org//C:ip/mozilla-trademarks an item in another part of the volume
a part atom/meadow a part (Comprise: a concern)
an exception form the manifest declares P:meadow Comprise's brand
a typed link {rel: depends-on, to: P:claim/meadow-closes-overnight} the item in its to
a sentinel none, self nothing, on purpose; the part itself
an open question {pending: "which entity is the licensor now?"} an answer still owed (section 10)
an address: an id, # and a field path N:audience/owners#who the item, and the field the path names in it (absent or open fields included)
a list of any of these parts: [V:file/readme-md, V:folder/guides] each of them

A path is not a reference. Files hold ids.

9.2 Two ends

Every reference must resolve. A reference that names nothing in the volume fails the check ref-unresolved, an error, unless the manifest's references.exceptions gives the case a lighter severity (Comprise: a vendor not yet fetched is a warning). A value in a reference field that has none of the forms above fails ref-grammar.

9.3 Resolution

  • A bare id resolves in its own part; a qualified id in the named part; a part id to the part. An address resolves as the id before its #, and its field path must parse (section 7.4); the field it names need not be present, since a question may be about a field nobody has filled (section 18.6).
  • Resolution runs against the loaded volume, never against the disk, and never depends on who is reading.
  • A URI written in a field (oes:comprise/meadow/meadow/O/role/Founder) is not a reference in this edition. It is kept as a value and not checked; resolving across volumes is reserved for a later edition.

9.4 Typed links

A typed link is a mapping {rel: <word>, to: <id>} in an item's links: list. It says how the item relates to the target, and the to is checked like any reference.

links:
  - {rel: depends-on, to: P:claim/meadow-closes-overnight}
  - {rel: defines, to: K:concept/close}
  • links: may also hold bare ids: links with no relation named.
  • Comprise also reads id: in place of to:. A link with neither is skipped.
  • rel is free text unless the manifest closes it with links.rels (0.0.1). The fabula closes it to nine words (section 18.4); a rel outside a closed list fails closed-list.

9.5 Relations are fields

There is no syntax for a relation other than a field that holds an id. A relation's name is its field's name (owner, parent, defined-by) or its typed link's rel. A format that needs a relation with attributes of its own (dates, shares, sources) makes it an item: Comprise's relationships between concerns are items of the kind C:bond.

9.6 Wildcard fields and literals

In a wildcard reference field (roles.*), a value is checked as a reference only when it is id-shaped: when it parses as an item id of a module the format declares. Any other string is a literal and is not checked:

roles:
  actor: E:org/meadow                    # an id: checked, must resolve
  condition: only after the bank feeds arrive    # a literal: kept, not checked

An id-shaped value that names nothing still fails ref-unresolved. In a named reference field (one without *), every value is checked, and a literal fails ref-grammar.

10. Open questions

An open question (pending) is a value nobody has yet given, written where the value would go:

terms: {pending: "funding amount and term are not published"}
feed: {pending: "not in FEED"}
pending: "Which entity holds the trademarks since the transfer?"
  • Pending beats plausible. A writer must never guess a value. It writes the question instead.
  • The form. {pending: "<the question>"} in place of any value, at any depth; or a pending: key on the item, for a question about the whole item. The question is a non-empty string; anything else fails the check pending-shape.
  • Who answers. The question should be addressed to whoever can answer it. A format may say who that is by default (Comprise: the item's owner; a role answers for itself; otherwise "unassigned").
  • Its address. The item's path plus # and the field path (…/P/offering/mozilla-festival#economics.price). A question on the whole item is addressed by the item's path alone.
  • What it does to the checks. An open question is never an error and never fails a reference check. A format's own rule that needs the value reports itself unverifiable instead of passing or failing.
  • The report. The checks list every open question with its item, its field path and the question (section 12.4).
  • Not the same as "not disclosed". provenance.state: not-disclosed records that the subject declined to say: a fact, not a question.
  • Derivations. A program that could not do its work writes a question, never a filler. When a fabula is made without a model, every item it writes says so: pending: "a model has not read this passage" (section 18.4).
  • Asking a person. An open question is the inline form. The core's dialectic (section 18.6) can put it to a person and record the answer; an answer of "I don't know" leaves the open question in place, in that person's words.

11. Ids, paths, URIs

Every item has an id, the primary key. Every part, module, kind, item and field has a path, the id respelled as a location. Every volume and everything in it has a URI, the path qualified with the format and the volume.

11.1 Ids

item-id      = module ":" kind "/" slug                 ; MacroCOSM's default form
qualified-id = part-prefix "//" item-id                 ; an item of another part (Comprise: "atom/" concern)
module       = %x41-5A                                  ; one capital letter the format declares
kind         = lower *( lower / DIGIT / "-" )           ; a kind that module declares
slug         = alnum [ *( slugch / "." ) slugch ]       ; [A-Za-z0-9]([A-Za-z0-9._@-]*[A-Za-z0-9_@-])?
alnum        = ALPHA / DIGIT
slugch       = ALPHA / DIGIT / "_" / "@" / "-"          ; a slug never ends in a dot
sentinel     = "none" / "self"
  • The manifest may declare other forms. ids.item-form gives the format's form and ids.item a regular expression for it; ids.brand-form and a kind's id: give exceptions; ids.qualified-form gives the qualified form. Comprise's brand is P:<slug>, with no kind. The product tree writes ids bare, <kind>/<slug>, with the module left out (section 18.2).
  • Bare inside its own part. An item's own id is written bare in its part's files. An id qualified with another part is an error (Comprise's check id-atom, which is its own).
  • Case is kept and significant. O:role/Founder and O:role/founder are two items. A tool that ever used paths as file names on a case-insensitive file system would merge them, so such a tool must refuse the pair.
  • An id outside the slug set (one with a slash in its slug, a colon, a #, a space or a non-ASCII letter) may still parse as an id where the format's id form allows it, but it has no path.
  • Never renamed. The id is the key. Renaming a thing changes its name.

11.2 Paths

A path is an id respelled as a location, through the levels the manifest's paths.levels declares.

Format Levels Item path
cosm (built in) module, kind, item, field P/<kind>/<slug>
canon (built in) module, kind, item, field V/<kind>/<slug>
fabula (built in) module, kind, item, field <module>/<kind>/<slug>
doc (built in) module, kind, item, field <module>/<kind>/<slug>
thym (built in) module, kind, item, field <module>/<kind>/<slug>
comprise (MiniCOSM) concern, module, kind, item, field <concern>/<module>/<kind>/<slug>
ascribe (MiniCOSM) module, kind, item, field <module>/<kind>/<slug> 
path      = [ part "/" ] module [ "/" kind [ "/" slug [ "#" field ] ] ]    ; part present exactly when the format has parts
part-path = part                                                           ; a part alone (Comprise: a concern)
field     = key *( "." key / "[" 1*DIGIT "]" )
key       = ( ALPHA / DIGIT ) *( ALPHA / DIGIT / "_" / "-" )

Properties.

  • A respelling. A path is computed from an id, and an id from a path, with no lookup.
  • Slug-based. Built from slugs, which never change when an item is renamed.
  • Absolute. In a format with parts, a path always starts with the part. There are no relative paths.
  • ASCII, and one spelling. No colon, so a path is safe as a file name on Windows; no percent-encoding, no .., no leading or trailing slash. A path has exactly one spelling, and a reader refuses any other rather than guessing.
  • An address, never a door. A path never touches the disk by itself. It names a row, and is resolved against the loaded volume. It is never joined to a folder to open a file.

The shorter forms name the levels above an item: <part>, [<part>/]<module>, [<part>/]<module>/<kind>. The module and kind levels have no id; the path is their only name. A field follows only an item.

Exception forms respell through the manifest's paths.map. Comprise's brand P:<slug> has the path <concern>/P/brand/<slug>, which is one-to-one because P:brand/<slug> is never a valid Comprise id.

Refused, never normalized. A reader refuses a path with: a leading or a trailing slash; an empty segment; a segment that is . or ..; percent-encoding, an encoded slash included; a backslash; whitespace, control characters or anything outside ASCII; a colon; a segment ending in a dot; a second #; a module the format does not declare; a kind its module does not declare; more segments than the format's levels allow; a segment that is a Windows reserved name (con, prn, aux, nul, com0 to com9, lpt0 to lpt9), in any case, alone or before a dot (con.txt, NUL.tar.gz).

Scope. A path to an item the reader may not see answers exactly as its id would: nothing there, no name. A path is never a way around visibility.

meadow/O/role/Founder O:role/Founder a role, case kept

11.3 URIs

For use outside one volume, a path is qualified with the format and the volume's database name:

uri      = "oes:" format "/" database [ "/" path ]
database = the catalog id without its prefix             ; holotype/meadow gives meadow; canon/~meadow-notes gives ~meadow-notes

oes:comprise/meadow                                      the Holotype itself
oes:comprise/meadow/meadow/O/role/Founder                a role in it
oes:canon/meadow-handbook/V/file/guides--close-md        a file in a Canon volume
oes:canon/~meadow-notes/V/file/plan-md                   a file in a project's catalog
oes:fabula/guides--close-md/P/claim/close-locks-the-day  a claim in a text's fabula
oes:emf/guides--close-md/P/claim/close-locks-the-day     the same claim, by the old spelling
oes:doc/macrocosm-oes/S/section/18.5                      a section of this specification's doc volume
  • No version. A URI carries no version, because a path keeps its meaning across every version of its format. A change that would alter what a path means must be a new format.
  • Old spellings. A URI whose format segment is the name of an old spelling (section 5.2) names the same thing as the URI with the format's own name: oes:emf/… resolves exactly as oes:fabula/…. A writer writes the format's own name. An old twin whose catalog id is emf/<slug> has the database name <slug>, the same as it would have under fabula/<slug>.
  • Unique within one install. A database name is unique among the volumes one reader knows, not in the world. A globally unique name, and a resolver for URIs across installs, are reserved for a later edition.
  • A private address. A URI names a place. It opens nothing to a reader who may not see what is there.
  • In enough. enough resolves URIs for its own volumes: oes:canon/<volume>/… for a Canon volume, oes:canon/~<project>/… for a project's catalog, oes:fabula/<twin>/… (or oes:emf/<twin>/…) for a fabula, oes:comprise/<holotype>/<path> for any Holotype Canon holds, and oes:doc/<document>/… for a doc volume.

12. Checks

12.1 What the checks are

The checks (lint) are the constraints of the database, run over the whole volume. The reader runs them on load, and an implementation may offer them as a command (enough's is lint, run over a volume). They never raise and never stop at the first problem. Each problem names its check, its item (or its file), the field path where it applies, and a plain message.

MacroCOSM defines a fixed vocabulary of generic checks that any reader can run on any volume from its manifest alone. A format may have checks of its own, written in its own code (Comprise's product-tree checks and its fourteen rules). The generic reader does not run those, and says so (section 12.3).

12.2 The generic checks

Check Default severity Catches
load error a file that does not parse, is not a mapping, or uses a forbidden construct; a nodes: entry with no string id; a volume layout that does not fit (a declared part with no folder, an undeclared folder); a refused declaration
duplicate-id error an id already loaded in the same module of the same part; the first wins
id-grammar error an id that does not parse in the format's id form
id-module error an id whose module the format does not declare, or, in a folder volume, an id whose module is not the module of the folder it is written in
type error a missing type, or a kind the item's module does not declare
type-prefix error an id whose kind disagrees with its type, outside the exception forms the manifest declares
identity-min error a field the manifest's envelope.required lists that the item does not carry; only presence is checked, as in Comprise, so an empty value passes
provenance error a provenance block missing where required, or malformed: a mode outside the list, sources empty or not a list, a confidence outside 0 to 1, a state outside the list
status error a status outside the status list
visibility error a visibility outside the visibility list
ref-grammar error a value in a named reference field that is not an id of a known form, a sentinel, a typed link or an open question
ref-unresolved error a reference that names nothing in the volume, unless the manifest's references.exceptions gives the case another severity
closed-list error a value outside its closed list, for any field the manifest's closed-lists names, and for a link's rel when links.rels closes it
pending-shape warning an open question whose question is empty or not a string
module-none warning a module: none with no reason
catalog-key error a catalog key the manifest's catalog.keys does not list (a note); a catalog id that fits neither catalog.id nor a form catalog.id-old lists, since the id names the database in every URI; a value outside the closed list the manifest gives a catalog key (section 13.5)
flavour error in a format with flavours, a catalog flavour outside the manifest's catalog.flavour list; an absent flavour reads as the manifest's catalog.flavour-absent
flavour-kind error an item whose kind lists flavours that do not include the catalog's flavour (section 7.3)

12.3 Which checks run

  • load always runs. A volume that could not be read cannot be checked.
  • The rest run when the manifest selects them, by id, in checks.envelope (and checks.load, which Comprise uses for load). A duplicate id is always reported; under duplicate-id when the manifest selects it, under load otherwise, which is how Comprise reports it.
  • An unknown check id in a manifest is kept and listed in the report as not run, with no error. Comprise's manifest selects checks the generic reader does not know (id-atom, source-undeclared, owner, vendor-missing, bond, aim and others); they are listed as not run, and a viewer says that Comprise's own rules need Comprise.
  • A format's own checks are named in the manifest's checks.own. Given as a list of ids, each is listed in the report as not run by a reader that does not run it, so a person sees what the generic checks left unchecked; given as a string, it is prose, kept and shown as it is.
  • The core's own checks. The dialectic's three, question-about, question-shape and session-declared (section 18.6.8), run on every volume that holds an item of module D. A reader that does not run them lists them as not run.
  • Severities. A check reports at its default severity unless the manifest's optional checks.severity mapping ({<check id>: error | warning | note}, 0.0.1) gives another. The mapping sets the severity of a check's findings except those that are fixed: a problem found while loading (load, and a duplicate id) is always an error, and two findings are always notes, an unlisted catalog key (catalog-key) and a legacy kind read under its new name (type). Outside the fixed findings the mapping may raise a default severity or lower it: Ascribe's manifest, for one, holds its own no-pii check to a warning in a holograph.

12.4 The report

report  = { errors, warnings, notes, pending, not-run, ok }
problem = { check, item (or file), field, message }
pending = { item, field, question }
ok      = true when there are no errors

ok is the verdict the generic checks give. A format may give further verdicts of its own (Comprise's "may this version be signed?", section 15).

12.5 Checks and writes

A format may say that every write goes through its checks and that a write which adds an error is undone. Comprise does. MacroCOSM does not require it: a reader may report problems after a write and keep the write. The dialectic holds its own writes to the rule: a write settle would make that adds an error is not made (section 18.6.4). enough reports the generic checks when a .cosm file is saved and never refuses the save.

12.6 What the generic checks do not verify

What a domain means. The generic checks say a volume is well formed and closed: every item is in a declared table, every required column is filled, every closed value is in its list, every reference has two ends. They do not say that a product tree balances, that a claim is true, or that a role is lawfully held. Those are a format's own checks, or a person's judgement. Ids that differ only in case, and slugs outside the path set, are not checked in this edition.

13. The manifest

13.1 What it is

A manifest is the machine-readable declaration of a format, a built-in or a MiniCOSM: what a program needs to read, check and render its volumes. It is one .cosm file, outside every volume. A volume names its format by its declaration and never embeds the manifest.

The word has a second sense in Comprise: the list of files and hashes in a saved version, a backup or a published concern. Both mean "the list of everything aboard". They never meet on screen.

13.2 Its format

A manifest is written in the COSM YAML subset and starts with its own declaration, manifest: minicosm/0: the manifest format, version 0. The value keeps the spelling it was first written with, for built-ins and MiniCOSMs alike, so that every manifest already written still loads. Words that YAML 1.1 reads as booleans are quoted in a manifest, so that a reader using any YAML loader reads it the same way.

13.4 Read generically

A generic reader needs only the keys above to load, check and draw a volume. Everything it does not understand it keeps. A manifest is never rewritten by a reader. The Comprise manifest that ships with enough is a byte copy of Comprise's own, refreshed from it and never edited in enough.

A manifest may also carry a moves: list: the moves its format declares for Thym, the language that composes them (https://thym.cosmoes.org/, where the block has a part of its own). Each entry names a move, what it takes and gives, its modifiers, whether it asks the model, the contract its output is held to, its rules-mode stand-in and its reference code. The generic reader keeps the block as one more key it does not use; the Thym compiler reads it, from every manifest in the registry, when it resolves a program's names. A format whose manifest is kept by another implementation, and copied into the registry unedited, declares its moves in a sidecar beside the manifest, <name>.moves.cosm, a mapping {moves-of: <format>/<major>, moves: [...]}: Comprise's is comprise.moves.cosm. A sidecar is not a manifest, and the registry passes it by; where a manifest and a sidecar both declare moves, the manifest's list wins.

The core's module D. The dialectic's module (section 18.6) is declared once, by the core, in a file of modules that ships with the manifests, core.modules.cosm, a mapping {modules-of: core, modules: {D: …}, closed: …} whose closed: is keyed by kind, then by field. Like a sidecar it is not a manifest, and the registry passes it by. A reader merges its module D, with the closed lists of D's own kinds, into every manifest that declares no module D, and adds D to a manifest's module segment where paths.segments.module lists the letters. A manifest that declares module D itself keeps its declaration, which is the dialectic's. Comprise's manifest, a byte copy, inherits D this way without being edited.

13.5 What 0.0.1 adds

Optional keys new in 0.0.1: volume.single-file, renderers[].lens, links.rels, closed-lists, checks.severity, Canon's catalog.scope, and the reserved macrocosm. A reader that does not know them keeps them and loses nothing it relied on before. The Changes appendix (section 21) records each.

Four more optional keys, which the reference implementation also reads:

  • module-file.items: where a module file's items are. A list of entries {key, kind, one, module}, of which only key is required. key is the top-level key of the file that holds items: a list of items, or, with one: true, a single item. kind is the kind given to an item written without a type (a single item always takes it). module limits the entry to one module. Without the list the reader reads the list module-file.shapes names (nodes:) and Comprise's root item of the product tree. The cosm manifest lists brand, firm, nodes, roles, externals and contracts.
  • A kind's own required, under modules.<letter>.kinds.<kind>: the fields an item of that kind must carry. It replaces the envelope's required-in-<letter> and required for that kind, and identity-min checks it. The cosm manifest's role, external and contract require only id.
  • catalog.<key>, where <key> is listed in catalog.keys and the manifest gives it a list: the closed list of values that catalog key may hold. Canon's scope (volume, project) and status (complete, ingesting, failed) are two. A value outside the list fails catalog-key; an open question passes.
  • A lens of a kind other than mermaid, under renderers[].lens.kind: DocOES declares a short and a table. A reader keeps it in the manifest for the code that renders it, and neither lists it among a volume's lenses nor draws it (section 14.3).

The core adds further optional keys, read the same way: core; declaration.old; catalog.id-old; a kind's flavours and closed; checks.own as a list; dialectic; and the core's module D (section 13.4). A reader that does not know them keeps them. Without them it refuses an old spelling and leaves module D undeclared, and every file it read before still reads.

13.6 The registry

A reader loads every *.manifest.cosm in its manifest folders into a registry. enough ships its manifests read-only; a folder for a person's own manifests is reserved for a later edition. The registry order is comprise, cosm, canon, fabula, doc, then any other in name order (ascribe, then thym). A manifest that does not load, or that names a format already in the registry, is skipped and reported; the first one wins. The registry keeps two lists, the built-ins (the manifests that say core: true) and the MiniCOSMs (every other); which list a manifest is in changes nothing about the order in which catalogs are identified. The registry is what step 1 of section 5.2 compares a declaration and its old spellings against, and what a refusal lists as known, each format with its old spellings after it.

14. Renderers and lenses

14.1 Renderers

A renderer turns a volume into another form. Renderers only read. Each applies the reader's scope first: a hidden item is absent from everything it makes (section 8.4).

A format's own renderers are its own (Comprise's 3D Overview, Field Guide, export and isotype). MacroCOSM defines three that any reader can make from a manifest alone: the text tree, the Mermaid lenses, and the item cards of a structured viewer.

14.2 The text tree

to_text_tree(volume) writes the volume as indented text: the catalog's declaration, id and name; then each part, when the volume has parts; each module by letter and name; and under each module its items, each as its name, its id and kind, and its summary. Items nest by parts and parent: a part under the item that lists it, an item under its parent. There is no line per kind and no per-kind count. An item that holds open questions is marked (N open), N being how many. The reader's command line prints it, and readvisor tools hand it to a model as context.

14.3 Lenses

Generic lenses. Every volume has the lens map, even when its manifest declares lenses of its own, unless one of them is named map: a flowchart of every module, with every reference field, every typed link, and every parts and parent as an edge. A Holotype is drawn this way, since Comprise's manifest declares its own renderers and no lens. A volume whose items carry parts or parent also has the lens tree, unless the manifest declares one: a flowchart of the items that are joined to another by parts or parent, with those as its only edges. A reader lists a volume's lenses in this order: the manifest's, then map, then tree.

14.4 How the generic renderer draws

to_mermaid(volume, lens) returns the Mermaid text and a node_map.

A flowchart:

  • each included module is a subgraph, titled with the module's letter and name;
  • each visible item of an included module is a node, labelled with its name (its id when it has none), shaped by its kind, and given the class class-by names, when there is one. The lens's shape for the kind decides the shape; without one, the kind's default does: the product tree's for brand, suite, offering, function, product, service, role and external, Canon's for folder, file and article, and a rectangle for any other kind;
  • each value of a listed reference field that resolves to a drawn item is an edge, labelled with the field's name; each typed link, when the lens lists links or that link's rel, is an edge labelled with its rel; each entry of a parts list and each parent, when listed, is an edge with no label, drawn from the parent to the part; references to items outside the drawing are left out;
  • node_map maps every Mermaid node id to its item's path, so a viewer can open the item a person clicks. A click line is written for each node only when the caller asks (clicks=True), because an item path is not a file path.

A mindmap draws the same items as a tree under the volume's name, with a branch per module and a leaf per item, and draws no edges.

A large volume. A drawing holds at most max_nodes items, 200 unless the caller says otherwise. Past that, the items left over in each subgraph (in a mindmap, under each module) collapse into one node labelled "… N more", N being how many; an edge to a collapsed item ends at that node, and in node_map that node maps to no item.

A local graph. Given an item (around: its key, id or path) and a depth (1 unless the caller says otherwise), to_mermaid draws only that item and the items the lens's edges reach from it or to it within depth steps, as one flowchart with no subgraphs, the item itself in the class focus.

A volume from text. load_volume_text(text, filename=…) reads one catalog held in memory, an example of this specification say, exactly as load_volume reads a file of that name, so it can be checked and drawn where it stands without writing anything to disk.

Well formed. Node ids are Mermaid-safe, unique in the diagram, and the same for the same volume every time; labels are quoted, so no label can end a subgraph or break a line; subgraphs balance.

15. Versions and signatures (by reference)

Defined here; specified in Comprise OES, in its section on versions (https://comprise.cosmoes.org/).

  • A saved version is an immutable copy of a volume's model files at a moment, with a manifest that holds every file's hash, the checks' verdict and its own hash. Taking one changes nothing.
  • A signed version is a saved version the checks allowed, whose files still match their hashes, signed by the holders of the roles that govern the volume.
  • The diff between two saved versions is item by item, with the field paths that moved.

Saving and signing are Comprise's; the generic reader does neither, and treats a Holotype's snapshots/ folder as outside the model.

Three other things carry versions, and none of them is a saved version: a format carries its major in the declaration (comprise/1, section 5); the manifest format is minicosm/0 (section 13.2); the grammar is 0.6.0, in the reserved macrocosm: key (section 5.6). A path and a URI carry no version (section 11.3).

16. The private/public split (by reference)

Defined here; specified in Comprise OES, in its section on the private/public split (https://comprise.cosmoes.org/).

The split is two documents, not one document with a setting.

  • Holotype — the complete, private description of one subject, kept by the subject, on the subject's machine.
  • isotype — a small public projection of the Holotype: a separate document with fixed fields, each derived from the Holotype by one rule, default-deny, released and signed by the subject. A field added to the model later never flows into it by itself.

The words come from taxonomy, where a holotype is the one specimen that defines a species and an isotype is a duplicate of it. In MacroCOSM they name the two halves of the split in every MiniCOSM, and both MiniCOSMs have one, since each describes a subject who keeps it private:

MiniCOSM The private volume Its public projection How the projection is made
comprise the Holotype the isotype by a fixed schema, each field derived by one rule (Comprise OES, its section on the private/public split)
ascribe the holograph the isograph, which the holder shares in private; the allograph, which the holder lists in the Allograph Registry by a Thym program the holder runs over the holograph (Ascribe, https://ascribe.cosmoes.org/, on projections)

A MiniCOSM with a split declares its public projection in its manifest (Comprise's and Ascribe's public-projection), and the rules of the projection are its own.

The core's built-ins have no split. They declare no public projection: a product tree, a Canon volume, a fabula, a doc volume and Thym's volumes are the owner's own files, and no reader sends them anywhere.

17. MicroCOSMs

Described in the map of the family at https://cosmoes.org/ and in the extension: block of Comprise's manifest; reserved for a later edition.

A MicroCOSM is one organization's extension of a MiniCOSM.

It may add: kinds, in any module; fields, on any kind; checks, including stricter versions of the MiniCOSM's own; renderers.

It may never: remove anything; rename anything; loosen anything (a closed list, a required field, a check's severity); change what a path or an id means; weaken the split, by adding to a public projection or opening anything by default.

What a MicroCOSM adds carries its name, <microcosm>.<kind> and <microcosm>.<field>, so that a later version of the MiniCOSM can never collide with it. A volume written with a MicroCOSM is still a valid volume of its MiniCOSM: a reader that does not know the MicroCOSM keeps its fields and ignores its checks.

How a volume says that it uses a MicroCOSM, and how a reader loads one, are reserved for a later edition.

18. The core

The core (section 3) is specified here: its registry and the model its built-ins share (section 18.1), each of the five built-ins (sections 18.2 to 18.5, and 18.7 for Thym's volumes, which Thym's own text specifies), and the dialectic, the one way any volume asks a person what its source means (section 18.6).

18.1 The core and its registry

What is built in. Every reader ships the five manifests of the built-ins, each saying core: true, and the file of modules that holds the dialectic's module D (section 13.4). They are read like any other manifest. Being built in means that a reader always has them, and that reading their volumes needs no specification beyond this one and Thym's.

The model. To decompile is to take an input apart into its fabula: everything that can be found in it or derived from it, enumerated item by item. To compile is to make a short of a fabula, its items said again in an order. The plainest thing that can be said of either is an atem. These are three densities of one meaning: the fabula is the material, a short is one arrangement of it, and an atem is a reduction, with a hermeneutic shape of its own (section 18.3.5). For code each density has a form of its own:

the input a text: an essay, a story, a poem, a song a folder of source

short a short: an entailment of the fabula in markdown, its items in an order (section 18.4.4) a cshort: source code rebuilt from the fabulac, to be read and never run

The flavour is a property of the fabula, named in its catalog; one format, fabula/1, holds all three (section 18.4). A running program is outside the model: nothing in the core runs a cshort, imports it or installs it.

An entailment is the step that expands meaning by reducing data, and it is also what that step makes. The whole entails what is made from it: an input entails its fabula, a fabula a short, and a short an atem; a codebase or an application entails its fabulac, and a fabulac a cshort or a catem; a Holotype entails its isotype and its paratype, and a holograph its isograph and its allograph. What is made says nothing its whole does not hold. It says it at a smaller size, or in another order or voice. An entailment made by rule, a projection (section 16), holds by construction. An entailment made by a model holds only because the contract's checks hold it: no-invention (it names nothing its whole lacks), stance-kept (it says no claim more strongly than its whole does) and coverage (each of its sentences traces to items of its whole), as Thym (https://thym.cosmoes.org/), its section 7.3, states them. Decompiling and compiling are both entailments; the move entail makes one by a model, and project makes one by rule.

The work is done by Thym's moves. derive decompiles and entail compiles; a fabula of code is built in stages, each one atomic run, and a job may resume between them (section 18.4.7); the dialectic's moves question, record and settle ask a person and fold the answers in (section 18.6). The moves are declared in the manifests (section 13.4) and specified in Thym (https://thym.cosmoes.org/), its sections 6.3 and 20. DocOES's byte-exact compile is a different act, which gives a document back from its own volume (section 18.5).

Models. A fabula records which model made it: the model's own id, its route (local, a model on the person's own machine, or cloud, a model reached through a broker), and for a cloud model its provider, once for each run that wrote into the volume (section 18.4.1). The model is chosen for each run: the same programs run on a local model at its best effort or on a cloud model through a broker, and nothing reaches a cloud model that the person did not choose for that run: a run that names no route runs on the local model. A run made without a model is in rules mode and says so. With its agent off, an implementation refuses every model, local or cloud (Thym, its section 19).

18.2 cosm: the product tree

What it enumerates. One whole's product tree, as COSM 0.2 and 0.3 wrote it outside any Holotype: the brand, and below it suites, offerings, functions, products and services, each answering the same nine questions (identity, flow, substrate, rules, principles, economics, vocabulary, affect, mattering). The context-ontology skill writes trees in this form. The built-in exists so that they open, check and draw beside everything else.

Its declaration. None of its own in the files: a tree's files say cosm: 0.2 or cosm: 0.3 (or opi:, the oldest form), and each reads as cosm/0. oes: cosm/0 is accepted too. enough writes no standalone trees.

Its volume. A folder of .cosm files. One holds brand: (COSM 0.2 said firm:, which reads the same), with the tree's roles:, externals: and contracts:; any file may hold nodes:; an optional doc.cosm holds reading:, history:, findings: and sources:, which carry the document rather than the model. The convention is three files, brand.cosm (or firm.cosm), nodes.cosm and doc.cosm; one file holding all of it is a complete tree too.

Its module and kinds. One module, P.

Legacy kinds read as current ones: firm as brand, stack as function.

  • Ids are bare. offering/ledger, service/reconcile; the brand's id is its slug alone (meadow). A reader treats them as P items: offering/ledger has the path P/offering/ledger, and the brand P/brand/<slug>.
  • The brand's kind is its block. The item under brand: (or firm:) is the brand; a reader sets its type to brand.
  • Roles and externals are reference targets, not items. role/<Name> names an entry of roles:, and ext/<slug> an entry of externals:. A reference to either resolves when the entry is declared.
  • Identity. Every item carries id, type, name, summary and owner (a role), with confidence and sources at its top level. Its sources should be declared in sources:.
  • The reference fields are the ones the tree's own grammar follows: parts, owner, flow.inputs.from, flow.outputs.to and substrate.depends-on (dotted fields, section 7.4), and a role's governs and escalates-to.

The tree's own checks (its levels, its flows, the seven conditions of equilibrium) belong to the context-ontology skill and to Comprise; enough runs the generic checks only. A product-tree file taken out of a Holotype (atoms/<concern>/P/brand.cosm) also says cosm: 0.3. Opened on its own it reads as a cosm/0 tree whose references outside P do not resolve; open the Holotype instead.

18.3 canon: Canon, the home file system

What it enumerates. A person's home file system, and what has been made from what it holds.

Canon is MacroCOSM's home file system: the volumes a person keeps, the file manager that browses them, and the derivations that turn their texts into fabulas and atems. enough's library is its reference implementation, and the names below that are enough's are given as its own. A Canon volume is a top-level folder of the home file system. Its catalog enumerates what the volume holds (folders, files, saved articles) and what has been derived from each file: its markdown twin, its fabula, its atem. The same built-in enumerates a project's files (section 18.3.4).

Its declaration. oes: canon/1. There is no legacy form, and a catalog without the key is refused.

Its volume. One file, canon.cosm, at the root of the volume's folder (volume.single-file: true).

  • enough writes it whenever it reconciles the volume, and only enough writes it. A write to it from the editor or from an agent's tool is refused ("change the volume's files instead"), and a change made by any other program is overwritten at the next reconcile. It is visible in listings, marked as the catalog.
  • .canon.json beside it holds the volume's fast-changing metadata (origin, ingest progress, fingerprint) and is outside the model.

18.3.3 Ids

An item's id is V:<kind>/<slug>, and its slug is its path, respelled: each / becomes --, each . becomes -, the result is lowercased, and any character outside a-z, 0-9 and - becomes -. A hyphen left at either end is trimmed. When two paths of one volume would give the same slug, each of them takes - and the first six hex digits of the sha256 of its path as a suffix. guides/close.md is V:file/guides--close-md. The path field keeps the real name, so nothing is lost; the lens's node_map is built from path.

The volume's own slug, in its catalog id, follows the same rule applied to its name.

18.3.4 The project catalog

A project gets a catalog too: rness/canon.cosm, with scope: project.

  • What it enumerates. Exactly what the project's file tree shows, minus rness/, which is enough's own machinery and holds the catalog itself. Dotfiles, ignored folders, and markdown twins with their asset folders stay out, as they stay out of the tree. Fabulas hide behind their sources. A folder holding a holotype.cosm is one item, not recursed.
  • Its id is canon/~<project-slug>, the project's name slugged; its URI is oes:canon/~<project-slug>/<path>.
  • Structure only. A project's catalog holds no size, no mtime, no timestamps, and no twin states: its twin and fabula entries carry the path alone, and a viewer works out the state when it shows one. The catalog changes only when files are added, removed or renamed, or when twins and atems appear, go or change, so a project kept in version control sees no churn from ordinary edits.
  • A cap. At most 5,000 items. Past the cap, the folders not yet enumerated are listed without their contents, each with its counts and pending: "too many files to enumerate here; open the folder in Canon".
  • When it is written. When the project opens, when Canon reconciles the project's pane, when the catalog is read through the cosm viewer, and after any derivation in the project. It is written only when its bytes would change, and never from the file tree's own refresh.
  • Write-refused like a volume's catalog.

How a project's catalog and a Canon volume's catalog of the same folder relate, when a project is copied into Canon, is reserved for a later edition.

18.3.5 Atems

An atem is the tightest fair, full, plain-English reduction of a text or of a passage of one. It has four parts.

Part What it is
the line one sentence of 15 to 25 words that says what the whole says. Fair: the author would accept it. Full: nothing the text depends on is missing. Plain: everyday words, no term the text did not need. In prose, "the atem" means the line
focus at most two sentences: what is happening in the text, the thing its author directs the reader's attention to
push one sentence: what the author wants the reader to take away, believe or do
pull one sentence: what the reader should actually take away: the usable point, with any hidden assumption, any opinion stated as fact, or any dependency the text leans on named plainly

Push is the author's side and pull is the reader's. They agree when a text is honest and complete; where they differ, the difference is the most useful thing an atem shows.

Three densities of one meaning: fabula · short (SHORT) · atem. A text's fabula holds its meaning item by item (section 18.4); a SHORT, which the fabula entails, says it again as prose, in an order (section 18.4.4); an atem says it in one line. The fabula is the material and a short is one arrangement of it. The atem is neither: it is a reduction, with a hermeneutic shape of its own in push and pull. A fabula of code has the same four-part atem, and its catem says at a chosen depth what a user can do with the program (sections 18.1 and 18.4.7).

  • Where an atem lives. In the text's fabula. A file's atem is the twin's atem: block (section 18.4). Asking for the atem alone makes a minimal twin, completeness: atem with nodes: []. A passage's atem is shown to the person first; when they pin it, it is appended to the twin as an item X:atem/<n> with the passage's span. Canon copies a file's atem line onto the file's item.
  • Only on request. An atem is made when a person asks (a click, a menu, a selection) or a readvisor's tool asks. Imports, ingests, listings and reconciles never make one.
  • Without a model, enough writes a labelled scaffold: the line is the passage's first sentence, cut to 25 words; the focus is its first two sentences; push and pull are open questions, {pending: "a model has not read this passage"}; the twin records derived.mode: rules, and the card says "scaffold, no model".

18.4 fabula: the fabula

What it enumerates. One input, a text, a poem or a folder of source code, taken apart into everything found in it or derived from it.

A fabula enumerates all the inspiration, meaning, intent, construction, production and assertions that can be found in an input or derived from it: what the work came from; the words it leans on, the particular things and people it names and the ideas it uses; what it sets out to do, for whom, and what it chose; how it is built; who made it, with what, and how it changed; what it claims, how it can be read, and what happens in it, in order; and its atems. A fabula is not a summary. It is the input taken apart into items that can be checked, drawn, compared and compiled into the shorts it entails. A text is what a person reads; its fabula is what the text holds, enumerated. Section 18.4.4 says where the word comes from.

Decompile, compile, atem. The fabula sits in the middle of a chain of entailments (section 18.1): its input entails it, and it entails its shorts and its atem:

  • decompiling an input makes its fabula;
  • compiling a fabula makes a short, an entailment of it (section 18.4.4), and for code a cshort, source rebuilt from it (section 18.4.7);
  • an atem says it most plainly (section 18.3.5), and for code a catem says at depth everything a user can do (section 18.4.7).

In a Thym program the two acts are the moves derive and entail (Thym (https://thym.cosmoes.org/), its section 6; for a folder of code, its section 20).

Three flavours. One format serves three kinds of input. A fabula's flavour says which, in the catalog's flavour key, and every module and kind of section 18.4.2 says which flavours may hold it.

A fabula's flavour is the kind of input it is the fabula of, from a closed list of three: fabulan, fabulap and fabulac. A fabula that names no flavour is a fabulan.

A fabulan is the fabula of narrative or non-fiction prose: an essay, a guide, a story, a report, a page of notes.

A fabulap is the fabula of poetry, metered verse or song lyrics. It adds the lines, the metre, the rhymes and the form, and lets several readings of one line stand side by side (section 18.4.6).

A fabulac is the fabula of code: a folder of source, enumerated as the specification of the program it holds (section 18.4.7).

Its declaration. oes: fabula/1. The fabula is one of the built-ins of the core (section 18.1), and its manifest ships with every reader. There is no legacy form, and a catalog without the key is refused. The fabula was first published under the declaration oes: emf/1. That value is an old spelling of fabula/1: a reader identifies it as a fabula (section 5.2), reports that it read an old spelling, and reads the file as a fabulan, since a file of that spelling never names a flavour. A writer writes fabula/1 and never emf/1, and a reader never rewrites a declaration it did not write: a file that declares oes: emf/1 keeps saying so until its text is decompiled again.

Its volume. One file. A text's fabula kept beside it is the text's twin, named by adding the flavour and .cosm to the text's whole name: close.md and close.md.fabulan.cosm, a poem rose.txt and rose.txt.fabulap.cosm. A folder's fabulac sits beside the folder: tool/ and tool.fabulac.cosm. A twin's source: names its input.

  • A fabula is identified by its declaration, never by its file name. A twin named as the first edition named it, the text's whole name with .cosm added (close.md.cosm), is read forever.
  • An old-named twin decompiled again. When a text whose twin has the old name is decompiled again, the new twin is written under the new name, the old twin's shorts: list is carried over into it, and the old file is then removed. This is the same act as refreshing a twin in place, under the new name. Nothing else ever renames or removes a twin.
  • Two names at once. If both close.md.fabulan.cosm and close.md.cosm exist, the one named with its flavour is the twin, and the old one is listed as an ordinary file with a note saying so. A text may have one twin per flavour.
  • A standalone fabula has no source: and is named <name>.fabulan.cosm, <name>.fabulap.cosm or <name>.fabulac.cosm; an old standalone <name>.cosm reads. It is read the same way as a twin.
  • One file, however large. A fabulac is one file whatever the size of its folder. A fabula kept as a volume of several files, for a very large repository, is reserved for a later edition.
  • The flavour of a text is the person's choice when the text is decompiled. An implementation may suggest fabulap for a text that looks like verse (short lines, stanza breaks, no headings) and fabulan otherwise.

The common rules.

18.4.3 The conventions, in plain words

Terms are grounded in FEED. Every L:term says where its word stands in FEED, the dictionary enough ships: feed: {word, pos, origin}, with pos the part of speech the work uses (one of those FEED lists for the word) and origin either feed or user (a person's own dictionary). Its sense is the meaning the word has in this work: FEED's definition when the work uses the word that way, the work's own sense when it does not. A word FEED does not hold is written feed: {pending: "not in FEED"}, an open question, never a made-up entry. In a fabulac the terms are the program's own vocabulary, grounded the same way.

Claim summaries name everyone. A claim's summary restates the claim as one sentence in which every participant is named, by its name or its id, and no pronoun stands in for anyone. A reader can take any claim out of the fabula and it still says exactly what it said.

Participants fill named role slots. A claim's roles: is a mapping from a role name to the participant that fills it: {actor: E:org/meadow, act: K:concept/close, after: E:thing/bank-feed}. The role names are free (actor, object, instrument, source, holder, cause, effect, condition …). A slot holds an item id whenever the participant is an item of the fabula, and is then checked; otherwise it holds a literal (section 9.6). The kinds with roles.* (influences, allusions, occasions, aims, voices) fill their slots the same way.

A claim's stance is how the text knows it. Every claim has one, from a closed list of six, in the spirit of the evidential markers some languages carry in their grammar:

Stance The text holds the claim as
axiom given, or true by definition; the text does not argue for it
observed seen, measured or done, at first hand
deduced reasoned from other claims of the text, which the claim links to with depends-on or supports
opinion a judgement or a preference of the author's
assumed taken for granted: the text relies on it without stating it as a premise, or supposes it for the sake of argument
hearsay reported from someone else, who fills the claim's source slot when the text names them

On every other kind, the stance is the fabula's. An aim, a line, a behaviour or a reading carries a stance from the same six, saying how the fabula knows the item: observed, read in the input (everything a rules stage reads from code is observed); deduced, reasoned from other items of the fabula; assumed, taken without support; hearsay, someone said so (an answer in the dialectic, a critic, a document); opinion, a judgement, such as a model's own reading; axiom, given. The two senses never mix: a claim's stance says how the text knows what it says, and any other item's says how its maker knows the item.

A claim's salience is how much it matters to the text, from a closed list of four: critical, high, normal and low. A short told by weight puts the claims in that order (section 18.4.4).

Typed links instead of arrows. A relation between two items is a typed link in the first item's links:, never a symbol between them. The fabula closes the relations to nine:

rel The item … the target
is-a is a kind or an instance of
part-of is a part of
depends-on holds only if the target holds
supports is evidence or an argument for
contradicts cannot hold together with
resolves settles (a question, a tension, a contradiction)
exemplifies is an example of
defines gives the meaning of
mentions names, without saying more about

Every other relation a kind needs is a named reference field, never a tenth relation: implementing is met-by, testing checked-by, being defined in a file defined-in; calling is depends-on, and a change that answers a question resolves it.

An item's span points it back at its input: it says where the item comes from, {lines: "3"} or {lines: "12-18"}, or, when lines do not serve, {start: "<up to 60 characters>", end: "<up to 60 characters>"}, quoted from the passage's first and last words. In a fabulac the span names a file as well, {file: days.py, lines: "9-16"}, its path relative to the source folder. A reader jumps from an item to its passage by its span.

Derived items carry their provenance. Every item says provenance: {mode, sources, confidence, state}. A decompile writes mode: derived, and its sources are locators in the input: the text's path and a line or a range, 'close.md#L3', 'close.md#L12-L18'; in a fabulac, a file's path, 'days.py#L9-L16'. What a person's answer wrote is mode: dialectic, its source the session it was given in (section 18.6). When an answer fills one field of an item made some other way, the item keeps its mode, the session joins its sources, and provenance.answered names the field: {<field path>: {sources: [D:session/<id>], confidence}}. A field a person declined to give is listed in the item's withheld, and its provenance.state is not-disclosed.

What was read is observed; what a model inferred says so. A fabula keeps apart what the input shows and what was made of it. An item read from the input, by rules or by a model, is observed, with a span that points at the words or the code. An item a model reasoned to is deduced; one it took without support is assumed; a reading that is the model's own is an opinion, whose: {by: model}, at a confidence of at most 0.5. Nothing a model supposed is written as though the input said it.

An unknown is a question, never a guess. What the input does not settle, who a poem's speaker is, why a decision was made, whether a behaviour is intended, is written {pending: "<the question>"} (section 10), or raised as a question of the dialectic about the item's field (section 18.6), and is answered by a person, never filled in by a model that does not know. A question can go to the author, an expert in the author's work, the program's maker, or anyone; its answer, even that the person does not know, is written back as section 18.6 says.

A fabula records which model made it. The catalog's derived names the model, its route and, for a cloud model, its provider; derived.runs names them for every run that wrote into the fabula; and every item's provenance names its mode and its sources. A fabula made partly on a local model and partly on a cloud model says which part came from which (section 18.4.1). Nothing reaches a cloud model that the person did not choose for that job, and a job that names no route runs on the local model, whatever entry point started it.

A scaffold says it is one. When no model is available, an implementation still writes a fabula, by rules: for a text, candidate terms and entities from the text and FEED, and atems as in section 18.3.5; for a folder, the outline of section 18.4.7. The catalog says derived.mode: rules. Every item a rules pass guesses at has confidence: 0.3, state: pending and pending: "a model has not read this passage", and the viewer says "scaffold, no model". What a rules pass reads exactly, a file's digest, a function's signature, a stanza's lines, is observed at full confidence. A scaffold is a starting point a person can see through, never a guess dressed as a reading.

Made on request, never in passing. A fabula is made when a person asks for it, or a readvisor's tool does. Nothing that imports, copies, lists or reconciles files ever decompiles an input, and nothing ever fetches an input that is not already on the person's disk.

Compiled, it entails a short. Compiling a fabula writes a short beside its input, a cshort or a catem beside its folder, and never touches the input (sections 18.4.4 and 18.4.7).

18.4.4 Shorts

A short of a text is an entailment of the text's fabula, compiled from it. Its name is an acronym, SHORT, syuzhetic-hermeneutic open readable text. It is syuzhetic: an arrangement, the fabula's items put in an order. It is hermeneutic: as it sets out each thing it says how the thing is known, every claim's stance in plain words. It is open: it is plain markdown that anyone can read without enough, it is yours to edit, it is honest about its gaps, and it is open to the reader's own reading. It is readable text: prose, not a database. The name covers only what is compiled from a fabulan or a fabulap.

One fabula, many entailments. A text's twin is its fabula (section 18.4): the order-free material every short is made from. Every claim is there with its stance, every event with its own before and after, every term grounded, and each item's span says where in the author's text it was found.

A syuzhet is an arrangement of a fabula's material, its items in an order. The author's text is a syuzhet of the same fabula, the first one, and it is the author's: it is never called a short, and it entails the fabula rather than the other way round. A short is a syuzhet the fabula entails, compiled from it, and a text can have many. The atem sits outside the pair. It is the breath of the text, a reduction with its own hermeneutic shape (push and pull), neither material nor arrangement.

Two orders. A short sets out the fabula's items in one of two orders:

  • as told — every item where its span puts it, in the author's order: told in the files;
  • by weight — the claims that matter most first, then the events, then the terms: weight in the files.
Order In words How it orders
told as the author told it every item with a span, in the order of its span: by first line, then last line, and within one line the words, the names, the ideas, the claims, then the events. Under the text's own headings when the text can be read (a span given as quotes is then placed on its line). Items that no span places come last, under "Also in the fabula"
weight by weight the claims in order of salience, grouped by the concepts they lean on; then the events, in before/after order; then the terms

Both open with the atem line, and both say each claim's stance in plain words ("the author holds that", "it is assumed that", "reportedly"). Pinned passage atems are not set out: like the file's atem, they stand outside the short. With no order given, a compile uses told when the fabula names a source text that can be read, and weight for a standalone fabula. Without a model a short is the ordered outline itself, said in the items' own sentences; with one, a model writes the outline as prose and is told which order it is in. A third order, the events first in the order they happened, is reserved for a later edition.

A short of a fabulap (section 18.4.6) goes stanza by stanza: how the poem is built, its form and its metre, then each stanza's lines with their stresses and rhymes (their words only where the fabulap holds them), its devices and its readings, each reading said as whose it is. Told by weight, it ends with how the poem can be read.

The file. A short is written beside its text as <text-stem>.short-<YYYY-MM-DD-HHMM>.md, in local time: notes.md gives notes.short-2026-10-23-1042.md. The stem is the text's, whatever the twin is called: the twins close.md.fabulan.cosm and close.md.cosm both give close.short-…md, and a standalone rain.fabulan.cosm gives rain.short-…md. A second compile in the same minute takes -2, then -3. Every compile is a new file. Nothing is overwritten, and the text is never touched. A short is an ordinary markdown file, shown in every listing; Canon's catalogs mark it short_of its text, and the text shorts (section 18.3.2).

The footer. Every short ends with one italic line that says what it is a short of, in which order, when, and by which model or by rules:

*a short of notes.md, told as the author told it, compiled from its fabula on 2026-10-23 by g40-04*

Without a model the line ends "by rules, without a model". A short of a standalone fabula says so: "a short of rain.fabulan.cosm, a standalone fabula, told by weight, compiled on …". A footer written by an earlier edition, which names the fabula by the name it had then, reads the same.

The fabula records its entailments. Each compile appends one entry to the fabula's shorts: list, {path, at, by, mode, order}: the short's file name beside the twin; when, as a timestamp in UTC; the model's id, or rules; model or rules; told or weight; and route, local or cloud, when a model wrote it. The list is made just above nodes: the first time. Nothing else in the fabula changes: not its items, not its source: (a fresh twin stays fresh), not a byte of the rest.

A fabulac entails a cshort. A fabulac's short is a cshort, source code rebuilt from the fabulac (section 18.4.7). It is recorded in the same shorts: list, with order: code, but it is a folder of source and not prose: the acronym SHORT names the entailment in prose and verse, and a cshort keeps only the word.

Where the words come from. Fabula and syuzhet are the Russian Formalists' pair: the story as it happened, and the story as it is told. Their work on how a telling makes the familiar strange began with Viktor Shklovsky's Art as Technique (1917), and Boris Tomashevsky's Thematics (1925) set the two terms out. MacroCOSM borrows the pair for meaning rather than plot: the fabula is the material, and a short is one entailment of it.

18.4.6 Verse: the fabulap

A poem asks more of a fabula than prose does. Its lines are units of their own, so each is a C:line with its number counted over the whole poem, its stanza, its stresses and its place in the rhyme scheme. Its metre and its rhymes are items, C:metre and C:rhyme, each naming the lines it governs and, for a metre, where a line departs from it. Its devices, its voice and its divisions are the prose kinds C:device, C:voice and C:part, with stanzas, verses, choruses, refrains and bridges among the divisions. Its occasions and allusions are I items; the book or the album it appeared in is an R:release. Rhymes are compared within a stanza, and the scheme's letters run on from one stanza to the next: a sound that comes back in a later stanza takes a new letter there, and a second C:rhyme.

Several readings stand side by side. A poem often means more than one thing at once, and a fabulap does not choose. Each interpretation is a P:reading whose of names what it reads: the line, the word, the image. Readings of the same thing stand together, each saying whose it is and what in the text supports it:

Whose whose stance Provenance
the author's, through the dialectic {by: author, session: D:session/<id>} hearsay mode: dialectic, its source the session
an expert's, through the dialectic {by: expert, name, session} hearsay mode: dialectic
a named critic's {by: critic, name, work}; a name not known is a question hearsay mode: derived, its sources the text
the model's own {by: model}; model defaults to derived.model opinion mode: derived, confidence at most 0.5
a reader's, a person's own note {by: reader, name} opinion mode: manual

grounds lists what supports a reading, each entry an item of the fabula and a sentence on why. Two readings that cannot both hold link with contradicts; one that builds on another links depends-on; readings that may both be meant carry no link, and intended, set by the dialectic, says which the author owns. A C:device says that a figure is there; a reading says what it means.

The author, or an expert in the author's work. A poem's fabula cannot be made well from the text alone: who speaks, what an image stands for, whether an ambiguity is meant, what was cut from a draft, only the poet knows, and after the poet an expert in the poet's work. The fabulap's bank of opening questions asks the author these things, and when the author cannot be asked the questions go to: expert. This is what the dialectic is for (section 18.6). Until a question is answered, its field stays pending and the readings stay side by side.

What a full fabulap holds. A fabulap made at its best guess holds what one reading finds. A full one is built by Thym's helper moves for verse, scan by rule and construe by a model (Thym (https://thym.cosmoes.org/), its section 20.9), and holds the poem along eight axes:

Axis What the fabulap holds Kinds Made by
sound each line's stresses and syllables; the end and inner rhymes, and the scheme; alliteration, assonance, consonance C:line, C:rhyme, C:device rule, from FEED's pronunciations
form the metre and its departures; the form the poem keeps, with each of its rules held or broken; where lines run on, and where they pause C:metre, C:form, C:line, C:device rule
structure the stanzas and a lyric's sections; refrains, repeated lines and openings, the hook; where the poem turns; what happens in it, in order C:part, C:device, T:event rule; the turn and the events by a model

What a rule reads exactly is observed, and what it reads through FEED's pronunciations is deduced. What a model writes keeps the stance the poem gives it: a reading is the model's opinion, at a confidence of at most 0.5, and an aim, an occasion or an influence the poem does not state is assumed, pending, and asked (Thym, its section 20.9).

The thresholds behind each rule are the conformance suite's. Syllables and beats are counted in English, through FEED, so a haiku is counted by English syllables. A poem that keeps no form of the table is named by its shape (four quatrains, rhymed abcb). The table is this edition's, and a later one may add to it.

The questions. The fabulap's bank asks the author, or an expert in the author's work when the author cannot be asked, along the same axes: what set the poem going and what was in the author's ear (inspiration); what a reader should feel by the last line, and what the poem is careful not to say (intent); who speaks, to whom, and whether the voice shifts (voice); how a line is read aloud, and whether a break, a sound, a departure from the metre or the form itself was meant (sound and form); which image weighs most and what a figure stands for (figure); whether an echo was meant and, when the author cannot be asked, whether every word is as the author left it (reference); whether a reading was meant, and which the author would refuse (what is left open); and, for a song, what it is sung to and where the tune moves a word (a lyric). Each question names the item it is about, and its answer is written as section 18.6.4 says: an answer that the author meant a reading, a device or a form sets its intended.

A lyric. A song's words are verse, and a fabulap holds them as it holds a poem's, with three things more. Its sections are the parts a lyric sheet labels, verse, chorus, bridge and the rest, and a chorus that comes back is one part sung again. Its hook, the line a listener keeps, is found by rule as the line said most often, held as a guess, and asked. Its sung line is not its spoken line: the fabulap scans the words as they are spoken, and says so. Without the music a fabulap cannot know the melody, where the tune puts a word's stress or holds one syllable over several notes, the rhythm and the pace of the setting, its harmony, which lines are sung and which spoken, or what a singer adds or repeats. It holds what the author or an expert says of them: the tune as an R:means and its maker as an R:maker of capacity composer, a recording or a performance as an R:release, and a stress the tune moves as a C:device at its line; never the notes.

What it leaves out. This edition's fabulap does not hold the music of a song (above); the poem on the page beyond its lines and stanzas (indentation, spacing, the shape the lines make, type, and the marks a line's text keeps when it is written); prosody beyond stress (the length of syllables, pitch and pace) and every prosody but English's, which FEED reads; the poem's life outside its text (drafts, variants, editions, translations, letters, the poet's life), which reaches a fabulap only as an answer; readings in a school's name, which reach it only as a named critic's or a reader's own; and a measure of the poem's style against the null morph, whose scales read prose (Thym, its section 13). Each is a place a later edition can add to, by declaration (Thym, its section 20.9).

A line's text is stored only when the source may be copied. C:line.text is written only when the person says the poem may be copied: it is their own work, or it is out of copyright. Otherwise the line's span is the pointer, and the fabulap holds the line's number, stresses and rhyme without its words. Nor are its words in its name: a line whose text is not written is named by its number (line 5). Single words the fabulap needs elsewhere, a term, a rhyme's sounds, an allusion's cue, are not the line's words, and are kept. A line's stance is that of its words; how sure its scansion is shows in its provenance's confidence. Nothing is ever fetched: a fabulap is made from the copy of the poem on the person's disk, and no implementation goes looking for a text, a draft or a critic's reading.

The kinds' fields are in section 18.4.2.

18.4.7 Code: the fabulac, the cshort and the catem

The model for code. A fabulac is the specification of a program: everything a competent programmer would need, with the fabulac alone, to write the program again. A cshort is source code rebuilt from a fabulac. A catem is a text that says everything a user can do with the program. All three are files that are read; the running program is outside this document, and no conforming implementation runs, imports or installs a program to decompile it or a cshort to show it.

A cshort is a fabulac's short: a folder of source code rebuilt from the fabulac alone, shown and never run.

A catem is a fabulac's atem at depth: a markdown text that says what a user can do with the program, at one of three depths, line, overview or manual.

What a fabulac holds, facet by facet.

Facet In a fabulac
inspiration the tools, programs and traditions it follows (I:influence); what prompted it or a change in it (I:occasion)
meaning its own vocabulary (L:term), the things it deals with (E), the ideas it relies on (K:concept)
intent its aims and audience; every N:use, one thing a user can do, end to end; its requirements, with force and what meets and checks them; the decisions recorded in its code, documents and history; what it deliberately leaves out (N:exclusion)
construction every file of the tree read (C:file); its components; every interface a person or another program reaches, with its exact signature; its structures; its behaviours; its dependencies and settings
production its makers, changes, episodes and releases, read from its history; the tools and languages it is made with (R:means); its licence (R:licence)
assertions what its documents claim (P:claim); its cases, from its tests and its documents (P:case); the steps of each use, in order (T:event)

How much detail is enough. Everything a user or a caller can observe is written exactly; everything that is a choice inside a function is left to whoever rebuilds it, unless an N:decision says why it matters.

Kind Enough Too much
C:file its path, language, one line on what it holds, the names it defines, its digest and length its contents, its imports one by one
C:interface the exact signature; every parameter with its type, default and meaning; what it returns; every error a caller can see, with its message when a user sees it; whether it is public its body, its local variables, the order of its statements
C:structure every field with its type, default and meaning; the invariants a rebuild must keep (ordering, uniqueness, what is never 0) how it is built in memory
C:behaviour what happens for which input, in plain words and in order: what is read, what is decided, what is written, what is printed; every edge case and error message a user meets; exact output formats where a test or a user depends on them a line-by-line paraphrase; loop variables; anything a competent programmer would choose the same way unprompted
P:case what is given and what is expected, exactly as a test or a document pins them the test's code
C:dependency, C:setting the name, the version constraint or default, where it is read, what it changes its documentation

A fabulac holds no function bodies and no paraphrase of code line by line.

The source folder and its licence. A fabulac's source is the folder (section 18.4.1), its freshness the tree digest. The licence is read from the folder and recorded twice: in source.licence and as an R:licence item. A folder with no licence file is still decompiled, with licence: {pending: "…"}, and a viewer says that the licence is a question (licence-recorded, section 18.4.8).

History. When the folder is a git clone, its history is read from the clone alone: its log, its tags, and the documents and change logs in the tree. Commits are grouped into episodes (R:phase), tags become releases, and authors become makers: by name only where the repository states that name itself (its licence's copyright holder, a line of an authors file, or an author or maintainer its packaging file names), otherwise as a numbered contributor, and never by address. An implementation may bound how much of the log it reads and how many changes it keeps as items; a history that does not reach the first commit says so, and what is not kept item by item is counted in its episode and its release (Thym (https://thym.cosmoes.org/), its section 20.6). A folder that is not a clone has only the history its own documents hold. Issues, pull requests and anything else held outside the clone are reserved for a later edition.

How a fabulac is built. In five stages, each one whole run that lands its result before the next begins:

Stage Asks a model Finds
survey no from the syntax tree and the files: every file, its components and interfaces with their names and parameters, its dependencies and settings, its licence and the means it is made with
history no from the clone: changes grouped into episodes, releases from tags, makers
read yes, once per file for each file, against the survey: behaviours, structures, cases from the tests, terms, concepts, claims, events
fold yes over the whole: aims, audience, uses, requirements, decisions, exclusions, inspiration, and the atem
question yes the dialectic's questions where the build was unsure (section 18.6)

A file's reading holds only what it adds for its file. It may add to an item of the outline of its own file the fields its kind takes that the outline lacks (an interface's takes, gives and raises; a structure's fields and invariants; a component's does; a setting's means), and add inside one (a parameter's means), never changing what a rules stage read.

After each stage the fabulac, with what the stage found, is written beside the folder, and a build that stops is resumed after the last stage that landed, as long as the tree digest has not moved. The fabulac's derived.runs lists every run. A build with no model runs the first two stages only and writes the outline: derived.completeness: outline, the files, components, interfaces, dependencies, settings, licence and history, with nothing read for meaning or intent. A Thym program that builds a fabulac is one file of five programs (Thym (https://thym.cosmoes.org/), its section 20). The host runs the file's programs as one job, in the order they are written, filling each program's fabula input with the fabulac the program before it landed, and a job that stops takes up again after the last program that landed. Each run joins derived.runs, naming its program in program (survey-the-repo) and its own trace in run.

What this edition specifies. A conforming builder handles pure-Python source that a person could read in an afternoon: no C extensions and no generated code, up to about sixty files and six thousand lines. Larger repositories, other languages and a fabulac kept as a volume of several files are reserved for a later edition.

The cshort. Compiling a fabulac writes a folder beside it, <name>.cshort-<YYYY-MM-DD-HHMM>/, holding the rebuilt tree and a CSHORT.md. The cshort rebuilds every C:file whose language is a programming language and that is not a test, nor a type stub (.pyi), nor the repository's own tooling (its documentation's build, its scripts, its examples and benchmarks), and the README; tests are rebuilt only when asked, since their content is held as P:case items. It also carries a packaging file written by rules, never by a model, from what the survey recorded (the project's name, its version where recorded, the Python floor, the dependencies and optional groups, and the modules and packages with their layout), its first comment line saying that rules wrote it from the fabulac, so that the rebuilt program can be installed and its tests run from the folder; where the survey recorded too little to write one truthfully, it writes none and CSHORT.md says why. CSHORT.md's first line is the footer, one italic line naming the fabulac, the language, the day of the run (in UTC) and the model: "a cshort of days.fabulac.cosm, in Python, compiled on 2026-11-05 by …". Then come a table of the files written, each with the C:file it came from (rules for the packaging file) and its sha256, what was not rebuilt, why no packaging file was written when none was, and, last, the source's licence line, Licence of the source: <source.licence> (with none recorded, Licence of the source: not recorded (<the open question>)). A compile is recorded in the fabulac's shorts: (section 18.4.1). One fabulac may entail a cshort in another language than its source's; the entry's language names the cshort's own.

A compile passes these checks, all without executing anything:

Check Holds
parses every rebuilt file in a programming language is parsed by that language's parser with no syntax error. Parsing is not running: nothing is imported, compiled to disk or executed
interfaces-present every C:interface of the fabulac is defined in the cshort's file it is defined-in, with the same name, the same surface and the same parameter names in the same order
files-present the cshort holds every file it is required to rebuild, at its path, and the packaging file rules write whenever the fabulac records enough for one, exactly as they write it; and the digests CSHORT.md lists are the files'
footer CSHORT.md's first line is the footer, naming the fabulac's file, the language, the day of the run (in UTC) and the model; its last line is the licence line, agreeing with source.licence
provenance the compile is recorded in shorts: with path, at, by, mode, order: code, route, language and files, and the footer names the run

A conforming implementation shows a cshort, its files and its CSHORT.md, read-only. It never runs, imports or installs a cshort or anything in it. Whether a cshort behaves as the original does is a question for a test outside the implementation, in a sandbox of its own.

The catem. Compiling a fabulac at a depth writes a markdown file beside it, <name>.catem-<YYYY-MM-DD-HHMM>.md, recorded in catems:. It ends with one italic footer line naming its depth.

Depth Says
line the atem's line: what the program does, in one sentence
overview every N:use, each with what a user types and gets
manual every N:use, and every interface a person reaches (the command line, the public functions), with what each does, its options and its errors

The fabulac's own atem: stays the four-part atem of section 18.3.5; a catem at depth line is that line.

An example. A program of one file, days/days.py, beside a README and a licence file holding the MIT licence:

"""days: how many days until a date, or since it."""
import argparse
import datetime as dt
import sys

__version__ = "1.0.0"


def parse_date(text: str) -> dt.date:
    """Read a date written YYYY-MM-DD, or the word today."""
    if text == "today":
        return dt.date.today()
    try:
        return dt.date.fromisoformat(text)
    except ValueError:
        raise ValueError(f"not a date: {text!r} (write it as YYYY-MM-DD)") from None


def between(start: dt.date, end: dt.date) -> int:
    """Whole days from start to end; negative when end comes first."""
    return (end - start).days


def say(n: int) -> str:
    """One line for a count of days."""
    if n == 0:
        return "today"
    word = "day" if abs(n) == 1 else "days"
    return f"in {n} {word}" if n > 0 else f"{-n} {word} ago"


def main(argv: list[str] | None = None) -> int:
    p = argparse.ArgumentParser(prog="days", description=__doc__)
    p.add_argument("date", help="the date, YYYY-MM-DD or today")
    p.add_argument("--from", dest="start", default="today", help="count from this date, not today")
    p.add_argument("--number", action="store_true", help="print the bare number of days")
    args = p.parse_args(argv)
    try:
        n = between(parse_date(args.start), parse_date(args.date))
    except ValueError as e:
        print(f"days: {e}", file=sys.stderr)
        return 1
    print(n if args.number else say(n))
    return 0


if __name__ == "__main__":
    sys.exit(main())

18.5 doc: documents (DocOES)

What it enumerates. One document, taken apart and given back.

DocOES, Documentation OES, takes a markdown document apart into items: its sections, the terms it defines, the complete examples it shows and the decisions it records. It joins them to items generated from the manifests (every format, module, kind, closed list, check and lens) and, for enough's own manual, to the help bubbles that sit beside the controls. A doc volume is a document's fabula: the material, item by item. Its short is the readable manual, compiled as told, and it gives back the markdown the author wrote, byte for byte. This specification is enumerated this way, and so is enough's Help Center, in each of its six languages.

Its declaration. oes: doc/1. There is no legacy form, and a catalog without the key is refused.

Its volume. One file per telling, <doc>.<lang>.doc.cosm: macrocosm-oes.en.doc.cosm, help-center.fr.doc.cosm. enough builds it at runtime into its own state from the markdown and the manifests, and builds it again whenever the document, a chapter, any manifest or enough's own version changes. It is never written by hand, never committed and never shown in the file tree. The markdown stays the authoring surface: to change a doc volume, change its document. The reference enumeration is enough's.

18.5.3 The conventions, in plain words

Every item has an atem. atem is the one line the atem density shows: two to fifteen words (in Japanese and Chinese, two to forty-five characters), one phrase, no final period, no ids and no markup, and unlike the atem of any other item with the same name. It is made by rule, never by a model. A section's atem is the first sentence of its first paragraph, cut at a clause break when it runs long; an HTML comment <!-- atem: … --> on the first line under a heading sets it by hand, as this section's does. A term's atem is its definition, and a reference item's is this specification's own line for it, or its manifest's subtitle. A model may offer a better line in the viewer, on request; it is never written into the volume.

Sections. Every heading of the document is a section, except a heading inside a fenced block. A numbered heading takes its number as its id: ### 18.3 canon: Canon, the home file system is S:section/18.3, and Comprise's #### P.3 is P.3. The title is S:section/root, any text before it S:section/front, and any other heading without a number takes its text, slugged: S:section/how-to-read-this. A section's body is the markdown between its heading and the next heading, verbatim and never re-flowed; heading is the heading line itself; lines says where both are, and order is the section's place in the telling. Its parts are the sections under it, and its parent the one above.

Terms. A term is enumerated where the document defines it in one of the conventions this specification and the Help Center already use: a table row whose first cell is bold; a bullet that opens with a bold phrase and a dash or a colon, - **term** — what it is; a paragraph that opens **term** is … or A **term** is …; and the first column of the "How to read this" table, which defines only the words nothing else defines. Where no convention fits, an HTML comment <!-- term: x --> before a paragraph makes the paragraph the definition of x. A term is defined once; a second definition is kept as also_defined_in and reported.

Mentions are computed. A section's mentions are the sections it names ("section 18.4", "sections 4 to 14") and the terms it uses, outside code. A term's use counts when it is written in bold anywhere, and in plain text when its name is distinctive (more than one word, or a capital or a digit inside it); in this specification every plain use counts. "Its section 10" names another document's section and is not a mention. What mentions an item is never stored: a viewer reverses the typed links when it loads the volume.

Examples. Every block marked cosm is an example, S:example/<n>, numbered through the document. Its body is the block, declares the format its declaration names, as a reference item, and in the section it is in. A block marked yaml or text stays part of its section's body. A viewer loads an example as a volume of its own, checks it and draws it.

Decisions. The numbered items of a section called "Decisions …" whose first words are bold are decisions, S:decision/<n>: the bold words are a decision's name, and about the sections and terms it names.

The reference, generated. For every manifest in the registry the volume holds R:minicosm/<name>, R:module/<name>.<L>, R:kind/<name>.<L>.<kind> with the kind's reference fields, checked fields, required fields and closed lists, R:list/<name>.<field> for each closed list, and R:lens/<name>.<lens>; and R:check/<id> for each generic check and each of DocOES's own, with the formats that select it. Each says where it came from: provenance: {mode: catalogue, sources: ['fabula.manifest.cosm#modules.P.kinds.claim'], hash}, the hash taken over that part of the manifest. The hand-written line for a check, a lens, a format, a kind or a value of a closed list stays in this specification's own tables, joined by the id in the first cell: the checks of sections 12.2 and 18.5.4, the lenses of section 14.5, the formats of sections 18.1 and 19, the kinds of sections 18.2, 18.3.2, 18.5.2 and 19.2, and the stances and relations of section 18.4.3. Nobody edits a generated item; its words are changed where they are written.

A chapter is a document synced into the volume, read-only, in its author's own words, recorded with the commit it came from and each file's sha256. A chapter's items take its prefix: a chapter with the prefix comprise gives S:section/comprise.4.1 and T:term/comprise.concern, and its S:chapter/<slug> item carries provenance: {mode: catalogue, sources: ['<repository> <path> @ <commit>'], hash}. A chapter's term with the name of one of the document's terms is same_as it.

References across volumes. Each doc volume has an inventory: one row per item, with its id, kind, version, anchor and atem. A chapter has an inventory of its own, named by its prefix. A reference into another volume, or into a chapter, is written <inventory>@<version>:<kind>:<id>, as in comprise@1:section:2.5, and kept in the item's xrefs. It is not a reference in the sense of section 9, since a URI between volumes is a value (section 9.3); the check xref-unresolved resolves it through the inventory instead.

A telling is one language a document is written in, a volume of its own. All the tellings of a document share one set of ids: the fabula has no language, and a section's name and body are its telling's. A translated telling takes its ids from the author's, its sections by number and its terms by their place in the section; where a place cannot be matched, the item is taken from the author's telling and says so, fallback: en. The word names this alone: what a fabula is compiled into is an entailment (section 18.1).

Voice. The catalog's telling names the voice a document is written in. The Help Center's is {lang: en, voice: rosa}, so a viewer can say who wrote it and a readvisor can quote it as hers.

Bubbles. In the Help Center's volume, each section of enough's help-bubbles document, or of its translation, is a bubble, B:bubble/<id>: its what, how and ideas verbatim, about the control it sits beside (its data-help id), and see the manual's sections it names. A bubble about another document names that document's sections instead, and keeps them as references across volumes, xrefs: the docs viewer's bubble points into this specification. Its atem is the first sentence of what.

Three densities. A viewer shows a doc volume at three densities: the fabula, each item as a full card; the short, the readable manual, compiled as told; and the atem, the document as an outline of its items' one-line atems. Compiled as told, a doc volume's sections, each its heading and then its body, in order, are the document again, byte for byte. That round trip is tested for this specification and for each telling of the Help Center.

In enough. The docs viewer shows the documents it holds at the three densities, from a project or from the home screen, with no model needed. It asks for one telling at one density (GET /api/docs?doc=&lang=&density=), and the volume is built the first time it is asked for, or again when its digest has moved; it draws a local graph around an item (GET /api/docs/lens, section 14.4), loads a live example as a volume from text (POST /api/cosm/inline), and gives back the markdown, byte for byte (POST /api/docs/compile). GET /api/docs/inventory serves the inventory. A readvisor asks the same volumes with the tool doc_lookup: a word, a section number or an id, answered with its atem, its definition and where it is defined.

18.6 The dialectic

The dialectic is the core's one primitive for asking a person what a source means and recording what they say. Every format inherits it: a fabula, a Canon volume, a document, a holograph and a Holotype ask and record the same way.

It exists because some of what a volume should hold is not in its source. A poem cannot be decompiled well without its author, or an expert in the author's work: who speaks, to whom, whether an echo was meant, what was cut. A fabulac improves the same way when the people who made the program say why a decision was made and whether a behaviour is intended. A person fills in a holograph by being asked about themselves, and a company fills in its Holotype by being asked about its concerns. In each case a program finds what it cannot know and a person says it.

A question asks one thing about one place in a volume. It is asked exhaustively but quickly: every question a volume raises is put to someone in the end, one at a time, in plain words, in no one's voice. A question never leads, never flatters and never speaks as the program or as anyone else; {name} and the item's own words are the only particulars it carries.

18.6.1 Two whole steps, never a waiting run

The dialectic is two runs with a person between them. Nothing waits inside a run.

  1. A run lands questions. A program (Thym's question move, section 18.6.7) reads a volume and writes its open questions into it as items. The run is atomic: it lands every question it raised or none.
  2. A person answers. At a screen, or through an agent that puts one or two questions at a time, the person answers, says "I don't know", declines, or skips. Their answers are recorded against the questions (record, by code and with no model), with the session they were given in: into the volume at once, or into an answers volume beside it that the second run reads (Thym (https://thym.cosmoes.org/), its section 22.2). No item the questions are about changes yet.
  3. A second run settles. A program (settle) folds the answered questions into the items they are about and lands the result, atomic in the same way.

Nothing partial is ever landed, and every run replays: a replay of either run needs neither the person nor the model. A volume between the two runs is whole and passes its checks; it simply holds open or answered questions.

Closed lists. why, kind, state (of a question) and through (of a session) are closed, as above; a value outside them fails closed-list. They apply to items of D only, never to a field of the same name in another module. answers.session and a session's asked, answered and skipped are reference fields and must resolve; an address resolves as section 9.3 says.

Ids. The slug of either kind is any slug of section 11.1. A session's slug may be session-<n> or elicit-<date>-<hex>, the spellings Ascribe and Comprise OES use: D:session/session-3 and D:session/elicit-2026-11-02-a3f9 are those sessions.

Where the items live. In a single-file volume, in the catalog's nodes: with the other items (section 6.5). In a folder volume, in module files in the place the manifest gives module D, in the part the questions are about; where a layout puts each module in a folder named by its letter, that folder is D. A question about an item of another part names it by its qualified id (section 6.4). A MiniCOSM's own specification may say where its volumes keep these items: Comprise OES keeps each session as a record under its catalog's sessions: and writes no question items, asking each bank question of a field directly (Comprise OES (https://comprise.cosmoes.org/), its section 8). An answer to such an address, asked without a question item, reaches an answers volume as an entry {about, answers} (Thym (https://thym.cosmoes.org/), its section 22.2).

Re-asking appends. A question keeps its id for its whole life. Answers are appended, never rewritten or removed, so a volume shows everything anyone said and when. At most one question is open for one address from one bank entry, move or person.

A decompile done again carries every D item over to the new volume when its about still resolves there, with its answers, its state and its sessions. A question whose about no longer resolves goes stale. Settled answers are not written again: the new decompile reads the source afresh, and an open question about what it found is raised anew.

"I don't know" is an answer. It is recorded, it closes the question, and the field stays open in the person's own words, which are a better question than the one asked. A refusal is a fact, not a question: the subject declined to say, and no later run asks the same person again unless a person opens the question again.

An answer about a whole item (about: <item id>). A value means the item must be read again (below). "I don't know" gives the item pending: "<the person's own words>". A refusal sets its provenance.state: not-disclosed and removes its own pending, and lists nothing in withheld, since no field was asked.

The provenance of what is written. A new item carries provenance: {mode: dialectic, sources: [D:session/<id>], confidence: <the answer's>}: the session is its source and the person's own confidence is its confidence. A field of an existing item leaves the item's mode and its provenance.state as they were; the session's id is appended to the item's provenance.sources, and provenance.answered gains one entry for the field, {<field path>: {sources: [D:session/<id>], confidence}}. An item with no provenance gains one: {mode: dialectic, sources: [D:session/<id>], confidence}, with that entry in answered.

Rules first, the model only to read again. settle writes every answer by rules, and asks a model only where an item must be read again in the light of an answer: a value about a whole item or about a span of the source, a value that would replace a mapping or a list in a field (other than a many list or a span), and a yes-no answer about a field that holds something other than true or false. A yes-no answer into a field that holds true or false, such as a reading's or a behaviour's intended, is written by rules. A run with no model leaves an answer that must be read again answered and unsettled.

A settle run is recorded. In a fabula, a settle run joins derived.runs and changes none of derived's single keys, which describe the last run that derived the fabula from its source (section 18.4.1).

A write that would add a check error is not made. The answer stays recorded and the question stays as it was, and a sibling question about the same address is raised with why: counter, asking again differently (a bank's counters give its words; section 18.6.6). While the counter question stands, the question it counters waits: no run tries its answer again, and settling the counter does not settle it.

18.6.5 Open questions and the dialectic

The two are one thing in two lengths. {pending: "…"} (section 10) stays the inline short form, written where the value would go, and every reader that lists open questions keeps working. A D:question is its long form: the same open question with an address, an answerer, a reason, a shape and a record of what was said. A question raised about a pending field is about: <item>#<field>, why: missing, kind: text, and asks the pending text with its first letter capitalised when it is a question; words that are not become one, made from the field and the item's name, with the words as its hint (What is the reason for "Not thread-safe"?). Settling an answer replaces the pending value; settling "I don't know" rewrites it in the person's words. A volume may hold either form, or both for one field, and neither is ever an error.

An item below confidence 0.5, or whose provenance.state is pending, raises one question about the whole item: why: unsure, kind: text, asking whether the item is right and, if not, what is, with its summary quoted. An item that holds a pending of its own raises the questions of its pending values instead, since they say what is unsure.

18.6.6 Banks

A bank is a format's list of opening questions, kept in its manifest's dialectic: key: what to ask of any volume of the format before anything else is known.

dialectic:
  writes: <one line: what an answer writes>
  answer-kinds: [text, choice, yes-no, number, date, ref, span]
  entry-fields: [id, about, asks, kind, options, to, why, many, hint, writes, only-with, at-most]
  banks:
    <bank name>:
      for: {flavour: fabulap}                # or {module: S}, or nothing: the whole format
      to: author                             # the default answerer; an entry may name another
      intro: <optional>
      counters: {<check id>: <question>}     # optional: the counter question for a refused write
      questions:
        - {id: speaker, about: C:voice#roles.speaker, asks: "Who is speaking in {name}?", kind: text, why: unsure}

An entry's about names a module (I: asked once of the volume), a kind (C:voice: asked of each item of that kind) or a kind's field (C:voice#roles.speaker: asked of each item where the field is absent or pending). An entry about a kind whose words fill nothing from the item (no {name} and no {<field>}) is asked once of the volume, about the kind's module, when the volume holds an item of that kind: a question that would be asked alike of each test case is one question. An entry may bound itself: only-with: <field> asks it only of an item whose field holds a value, and at-most: <n> of at most n items, those a person can best speak to: a command first, then a public name at the top of its module, then a public method, never first a private, dunder or abstract one; a setting a user sets before a constant; a change whose words say something before a release or a change-log entry; within that, what the reading marked unsure, then what carries an edge; ties to the newest. A field entry is not asked of an item that holds a pending of that field's name: the pending asks it. {name}, and any {<field>}, are filled from the item when the question is raised. A raised question's raised.from is <bank name>/<entry id>. An entry about a module may say writes: the kind (<kind> of that module, or <M>:<kind>) that a new item written from its answer takes; absent, the module's kind named like the entry's id (an entry audience about N writes an N:audience), where the module has one, else the module's first kind (section 18.6.4).

The older shape keeps reading: dialectic: {questions: {<letter>: ["…", …]}} is one bank, named after the manifest, each string an entry {about: <letter>, asks: <the string>, kind: text, why: missing} with the bank's default answerer. A manifest may hold either shape, and a reader reads both.

A bank may keep its questions in a file of the format's own, named in from: <file> in place of questions; a reader that does not have the file reads the bank as one with no questions.

Each format carries its own banks. The fabula carries one bank per flavour (section 18.4). Ascribe's opening questions are a bank (Ascribe (https://ascribe.cosmoes.org/), its section 8), and so are Comprise OES's, module by module (Comprise OES (https://comprise.cosmoes.org/), its section 8). This text specifies neither. The source ids session-<n> and elicit-… written before this edition stay valid spellings of a session: a bare session-1 in provenance.sources names D:session/session-1 whether or not the volume holds that item.

18.6.7 The moves

The dialectic's three moves are Thym's (Thym (https://thym.cosmoes.org/), its section 22), declared with the core's: question lands a volume's questions, from its banks and its open questions by rules and from a model where the volume is unsure, ambiguous, in conflict or silent on intent; record writes a person's answers into the questions, by code and with no model; settle folds the answered questions into the items they are about. Their contracts are addressed (every about and every answer names something that resolves), no-duplicate (no two open questions ask the same thing of one address), only-the-asked (only what the questions are about changes), and provenance (every field written carries the session as its source).

Check Severity Catches
question-about error an about that names nothing in the volume: an item that does not exist, a field path that does not parse, a span of the wrong shape (in a fabulac, one whose file or lines do not exist), a module or kind the format does not declare. A question that has settled, or whose state is stale or withdrawn, is skipped, since its answer may have removed what it was about, or it has ended because what it was about is gone

18.7 thym: Thym's volumes

What it enumerates. What Thym, the transcognition language that connects OESes, reads and writes. thym/1 is a built-in of the core, specified in Thym's own text and never a MiniCOSM. A thym/1 volume is one of seven kinds: a program volume, the enumeration of one .thym file, compiled back byte for byte; a morph volume of style sheets, measured against the null morph or declared by hand on ten scales; a context volume of occasions; a plan, what a program will do before it does it; a trace, what a run did, one record per node; a package, the catalog of a text's self-contained export; and a folder, a run's snapshot of a folder it took, every file's digest and every text file's bytes, so that the run replays without the folder. The full specification is Thym (https://thym.cosmoes.org/), its section 17, which this section summarizes.

Its declaration. oes: thym/1. There is no legacy form, and a catalog without the key is refused.

Its volume. 19.2 ascribe: a person's holograph

What it enumerates. One person, described well enough that no name is needed. Ascribe's volume is a holograph: the whole self, private, kept by its subject, as a Holotype is a company's. It holds what the person is drawn to, believes, worries about, has lived through, wants to know, thinks, feels, can do, understands and longs for, each item anchored to the thing it is about. There is no kind and no field for a name, an email address, a phone number, a postal address, a birth date, a government id or an employer's legal name; people in a person's life appear by what they are to the holder or by a pseudonym the catalog declares. The full specification is Ascribe (https://ascribe.cosmoes.org/); this section says how it sits in MacroCOSM.

Its declaration. oes: ascribe/1. There is no legacy form, and a catalog without the key is refused.

Its volume. A folder whose catalog, holograph.cosm, is the self: id: ascribe/<hid> (twenty-six characters of lowercase base32, the shape of a Comprise Connect hid), a pseudonymous handle, an optional one-line summary, pseudonyms and sample. Beside it sit the module folders, A/ to Y/, F/ and, for the dialectic, D/, each holding .cosm files of nodes:. The catalog may carry a few nodes of any module in its own nodes:, which is how the example below is one file. A .ascribe-private marker names files that every ingest, package, transfer and projection leaves behind.

Its modules and kinds. Ten containers of the self, one kind each, the kind the singular of the module's name and the letter its initial, and F for what they anchor to.

Kind Module What it is
affinity A Affinities something the person is drawn to, or turns from
belief B Beliefs something the person holds to be true
concern C Concerns something that weighs on the person
experience E Experiences something that happened to the person, or that they did
interest I Interests something the person wants to know more about
opinion O Opinions something the person thinks, and would say so
quale Q Qualia how something feels from the inside
skill S Skills something the person can do
understanding U Understandings something the person has come to understand
yearning Y Yearnings something the person longs for
form F Forms a thing a self can be about, grounded in FEED where it is one word FEED has
polyform F Forms several forms taken together, with the links between them
relation F Forms a relation the author declares beyond the starter list, named by its slug

Its envelope is Comprise's, so that the same moves work on both subjects, plus six fields of Ascribe's own: form (what a node is about: every node of the ten kinds names a form or a polyform), of and parts (a hierarchy, a branch or a flat list, as the author likes), when (a date, a year or an era word), valence (for, against or mixed) and strength (1 to 5). Typed links use a starter list of relations (is-a, part-of, about, because, before, after, with, against, like, from, toward, see) or a relation the holograph declares; the manifest keeps links.starter rather than a closed links.rels, so the generic reader lets a declared relation through and Ascribe's own check closes the list.

In enough. The reader loads, checks and draws a holograph like any volume, titled by its handle. Ascribe's own checks (an anchored form, a declared relation, the shape of a when, the range of a strength, what reads like personal data, and what a private marker would drop) are enough's (its ascribe lint command runs them over a holograph's folder), and a generic reader runs none of them. The personal-data check warns in a holograph and refuses a projection while it finds anything. The opening questions its manifest's dialectic: block holds are a bank of the core's dialectic, and a holograph's sessions and questions are items of module D (section 18.6). Ascribe's projections, the isograph and the allograph, and the Allograph Registry where a holder lists an allograph belong to Ascribe's own specification.

20. Conformance

20.1 A reader must

  1. Read a catalog and identify its format by section 5.2; refuse an unknown format or major, a value not spelled exactly (comprise/01, a value with spaces around it) or an empty declaration, with a plain error that names what the catalog declares and what the reader knows; return the refusal as a value and never raise.
  2. Read every file as UTF-8 with an optional byte-order mark, LF or CRLF, YAML 1.2 booleans and SafeLoader's other resolutions (section 4.3); report anchors, aliases, tags and multiple documents as load problems without crashing; never stop at the first problem.
  3. Find a volume's items where its manifest's volume block says they are (section 6), keep the first of two items with one id, and report the second.
  4. Keep every unknown field, unknown catalog key and unknown manifest key, and never drop one when it writes.
  5. Resolve references against the loaded volume (section 9.3); treat a path as a respelling of an id; refuse a malformed path rather than normalize it; never touch the disk to resolve a path.
  6. Run load always, and the generic checks the manifest selects; report unknown check ids as not run; report open questions with their item, field path and question (section 12).
  7. Apply visibility before showing or drawing anything (section 8.4).
  8. Keep macrocosm: and ignore it.
  9. Read every old spelling a manifest lists as the format it stands for, and report it as old: oes: emf/1 as fabula/1, a catalog id emf/<slug> with its database name, and a URI oes:emf/… as oes:fabula/… (sections 5.2, 6.2 and 11.3).
  10. Give every format the core's module D where its manifest does not declare it, run flavour and flavour-kind where the manifest selects them, apply a kind's own closed lists, and list a format's own checks as not run when it does not run them (sections 12.3 and 13.4).

20.2 A writer must

  1. Write the declaration first in a new catalog, and never rewrite the declaration of a volume it did not create.
  2. Write only the COSM YAML subset: no anchors (copy values instead of sharing them), no aliases, no tags, one document.
  3. Write ids in the format's form, with the kind equal to type, and never rename one.
  4. Write an open question, never a guess; give every fact its provenance.
  5. Keep the fields it does not understand when it rewrites an item.
  6. Write nothing into a file that its format keeps out of files (Comprise's people).
  7. Where its format says that checks gate writes, leave the volume's checks no worse.
  8. Write a catalog that a program owns (a Canon catalog) only from that program; and make derived items (a fabula, an atem) only when a person or a readvisor asks.
  9. Write a format's own declaration value, never an old spelling: oes: fabula/1, never oes: emf/1; a URI with the format's own name; and a new catalog id in the manifest's catalog.id form. Leave an old spelling where it finds one (section 5.5).

20.3 The conformance corpus

A reader conforms to MacroCOSM OES when:

  • Comprise's four public sample Holotypes (meadow, khan-academy, mozilla and wikimedia; 1,010 items between them) load through the generic reader and Comprise's manifest with no load problems, and every item has the path Comprise gives it;
  • every block marked cosm in this document loads, identifies as the format it declares, and passes the checks its manifest selects with no errors; among them the fabula's examples of section 18.4, one of each flavour (a fabulan of a short guide, a fabulap of a poem and a fabulac of a small program), and the twin that keeps the old spelling oes: emf/1, which identifies as fabula/1, old;
  • the fuller fabulac the reference implementation's corpus carries beside its program, a program of several modules with a history and tests, loads and passes the same way;
  • every path in the table of section 11.2 resolves to the id beside it;
  • each refusal case of section 5 (an unknown format, an unknown major, a misspelled value such as comprise/01 or ' emf/1 ', an empty oes:, a catalog with no declaration at a name no default claims) is refused, and each legacy case and each old spelling is read.

Where the reference implementation's tests and this list disagree, one of them is in error; the Changes appendix (section 21) records which was corrected.

20.4 Where an implementation and this text disagree

Where an implementation and this text disagree, one of them is in error. The disagreement is settled by correcting the one that is wrong, and the Changes appendix (section 21) records which was corrected, with the section it touched. No disagreement stands as a rule of its own.

Edition 0.6.0 · 2026-11-06. MacroCOSM is an OES with a core.

  1. The taxonomy. MacroCOSM OES is an OES: the grammar and the core built into it. The core holds five built-ins, cosm/0 the product tree, canon/1 Canon, fabula/1 the fabula, doc/1 documents and thym/1 Thym's volumes, each declared by a manifest that says core: true; a built-in is never a MiniCOSM. There are two MiniCOSMs, Comprise OES and Ascribe, each with a specification of its own. What a declaration names is a format, and the grammar's nonterminal minicosm is format (sections 3, 5.1 and 18.1).
  2. Section 18 is "The core". It opens with the core and its registry (18.1, new); the product tree, Canon, the fabula and documents keep their numbers (18.2 to 18.5); the dialectic is 18.6 (new); Thym's volumes stay 18.7. Comprise and Ascribe moved from 18.1 and 18.6 to a new section 19, The MiniCOSMs (19.1 and 19.2), which say how each sits in MacroCOSM as its own text now specifies it (Comprise's sessions and codebases, Ascribe's module D, private filter and projections), and Conformance, Changes and Withdrawn moved from 19, 20 and 21 to 20, 21 and 22.
  3. Canon is the core's home file system, specified apart from any one implementation; enough's library is its reference implementation. A file's twin is named in its fabula field; emf, the field's old spelling, is read as fabula (section 18.3.2).
  4. The name EMF is retired. The format is the fabula, declared oes: fabula/1. oes: emf/1 is its old spelling, read forever as a fabula whose flavour is fabulan and never written; a catalog id emf/<slug> and a URI oes:emf/… are read with it, and the check name emf-checks is read as fabula-checks (sections 5.2, 5.4, 5.5, 6.2, 11.3 and 18.1). A twin is named after its text and its flavour, and an older twin's <text>.cosm reads as it is (section 18.4).
  5. The fabula's flavours and four new modules. One format holds three flavours, fabulan (prose), fabulap (verse) and fabulac (code), named by the catalog's flavour:. Four modules join L E K P T X, whose kinds, fields and closed lists are unchanged, so every older twin is a valid fabulan: I Inspiration, N Intent, C Construction and R Production. A fabulac is compiled into a cshort and told as a catem; a fabula records the model, route and provider of every run that wrote into it, a settle run included, while derived's single keys describe the run that derived it (sections 18.1 and 18.4). A fabulap gives each line, its metre and its rhymes items of their own, and lets readings of one line stand side by side (section 18.4.6). A fabulac is the specification of a program, enough to write the program again from it alone; its source folder is fingerprinted by the tree digest; a cshort is a folder of rebuilt source with its CSHORT.md and a packaging file written by rules, never by a model, checked without executing anything; and no conforming implementation runs, imports or installs a program to decompile it or a cshort to show it (section 18.4.7). The fabula's own checks are listed in section 18.4.8.
  6. The dialectic. One primitive of the core asks a person what a source means and records the answer: module D, with the kinds question and session, which every format inherits; the opening questions as banks under a manifest's dialectic: key; an entry may bound itself, only-with: <field> and at-most: <n> (section 18.6.6); and Thym's moves question, record and settle. A session lists the questions it asked, or, where a format asks from a bank without writing question items, the addresses it asked; a MiniCOSM's own text says where its volumes keep the items; a settled question whose answer removed its item is closed, not an error. An item records what an answer filled in provenance.answered, and what its subject declined in withheld. The dialectic's checks run on every volume that holds module D (sections 8.5, 10, 12.3, 12.5, 13 and 18.6).

A reference may be an address, an id with # and a field path. Two generic checks are added, flavour and flavour-kind. The registry order is comprise, cosm, canon, fabula, doc, then any other by name, and the registry keeps the built-ins and the MiniCOSMs as two lists (sections 7.3, 9.1, 12.2, 12.3 and 13).

Version 0.0.1 · 2026-10-23, the grammar unchanged. Shorts and DocOES.

  1. What is compiled from a twin is a SHORT, written beside the text and recorded by the twin. One fabula, many tellings: the EMF twin, enumerated meaning fabula, is the material and a short one arrangement of it. The author's text is the first arrangement and is never called a short; the atem stays outside the pair. Every compile is a new file in one of two orders, the author's or by weight, and the twin lists its shorts so the material knows its tellings.
  2. A document is enumerated in its own grammar. The markdown stays the authoring surface, the volume is built at runtime and never committed, every item carries a one-line atem made by rule, and this specification's own tables are the hand-written overlay on what is generated, so nobody edits a generated item.

Version 0.0.1 · 2026-10-22. The grammar written down apart from any one domain.

  1. MacroCOSM is the grammar Comprise mapped, made real. Not a new taxonomy: Comprise OES already held every part of the grammar, and a second one would split the family.
  2. The format does not change. One loader, Comprise's, for every .cosm file; every existing file reads as it is.
  3. One declaration grammar, oes: <minicosm>/<major>, for every MiniCOSM, each manifest naming the legacy forms it reads: one line a person sees without parsing the file.
  4. An absent-declaration default claims only its own catalog file. Comprise reads a holotype.cosm without oes: as comprise/1; a default applied everywhere would claim every YAML file a reader was shown.
  5. A refusal is a value, not an exception. A viewer shows the refusal in place of the volume and goes on.
  6. macrocosm: is reserved and ignored. Room for a grammar version test, without refusing any file.
  7. Single-file volumes. A Canon volume and an EMF twin are one catalog each; a folder per text would double every tree.
  8. Module letters are local to a MiniCOSM. The declaration says which language a volume speaks; letters reserved across languages would run out and buy nothing.
  9. Paths drop the part level when a MiniCOSM has no parts. A single-file volume has one implicit part, and a segment that never varies is noise.
  10. Wildcard reference fields check only id-shaped values. Role slots mix item ids with literals such as conditions; literals checked as ids would make every condition an error.
  11. Link relations may be closed. EMF closes them so that twins can be drawn and compared; Comprise keeps its own free.
  12. Closed lists and severities by name, in the manifest. A MiniCOSM's own vocabularies (stance, salience) and its severities are checked without new code.
  13. Lenses are declared in the manifest, with a default. A MiniCOSM can be drawn without code; Comprise's manifest, a byte copy that declares no lens, draws with map.
  14. Generic checks only. A MiniCOSM's own rules are its own code; Comprise's fourteen rules are not reproduced in the generic reader, and a viewer says plainly that they need Comprise.
  15. Checks may gate writes; MacroCOSM does not require it. Comprise undoes a write that adds an error; enough edits raw text and reports problems after a save, never refusing it.
  16. load always runs. Nothing can be checked that was not read.
  17. Versions, the split and MicroCOSMs are by reference. Saved versions, signatures and the split are Comprise's (Comprise OES, its sections on versions and on the private/public split); MicroCOSMs are reserved for a later edition.
  18. A URI between volumes is a value, not a reference. Resolving across volumes needs a registry of volumes the grammar does not define.
  19. The EMF twin's name adds .cosm to the text's whole name. notes.md and notes.md.cosm sort together and pair by name; the family keeps one extension.
  20. An EMF twin's id respells the text's path. Two texts with the same name in different folders must not share an address.
  21. A project's catalog records structure only. No sizes, times or twin states, so that a project in version control does not change with every edit.
  22. An atem is a line with focus, push and pull, and "the atem" in prose is the line. One sentence is what a person keeps; the three vectors are what a reader needs to trust it.
  23. Without a model, a labelled scaffold. A derivation that could not read writes open questions and says so, never a filler.
  24. The specification shipped inside enough, beside the reference reader (superseded in edition 0.5.4 by the canonical edition at https://macro.cosmoes.org/).
  25. All rights reserved for the specification and the manifests; the reference implementation is licensed on its own terms.
